# SurvivalGames を 1 つの JVM で複数の試合を動かす形に作り直す — 洗い出しと計画（2026-11-03）

対象は SurvivalGames（`developments/SurvivalGames`）です。土台は Athena の `feature/world-threads`（server 0395・api 0061）です。この文書はソースを読んだ結果で、まだ何も書き換えていません。読んだのは `origin/v2`（3279a7f）で、本体 94 ファイル・試験 20 ファイルです。

## 1. 目標

- 1 つの JVM で、試合（以下「部屋」）をいくつも同時に動かす。VPS-B の実測では、1 GB の箱で 12 試合（288 人）が上限の目安。
- 部屋ごとに、今の SG と同じ流れ（ロビー → PreGame → Live → PreDeathmatch → Deathmatch → End → Cleanup）を回す。
- 1 つの部屋が固まっても、例外で止まっても、ほかの部屋とロビーは止まらない（Athena のワールドごとのスレッドを使う）。

## 2. 今の SG が「1 つの JVM で 1 試合」を前提にしている箇所

| 箇所 | 今 | 部屋ごとにするには |
|---|---|---|
| `SurvivalGames`（本体） | `Game`・`StateFactoryImpl`・`Arenas`・`Scoreboards`・`ServerStatusListener` を 1 つずつ持つ。ゲームループは Bukkit のスケジューラで 1 本（1 秒ごとに `game.second()`） | 部屋（`Room`）がこれらを 1 組ずつ持つ。ループは部屋のスレッドで回す（`Athena.runOnWorldTimer`） |
| リスナー 20 個（`@EventHandler` 74 個。多いのは `GameEventListener` 15・`CountdownListener` 14・`LobbyListener` 10） | `factory::match`（試合はサーバーに 1 つ）を見る。24 か所 | イベントのプレイヤーやワールドから部屋を引き、その部屋の試合を見る |
| `Arenas` | ワールド名は `sg-{マップの id}`。前の試合のマップを捨ててから読む | 名前に部屋を入れる（`sg-{部屋}-{マップ}`）。同じマップを 2 つの部屋が同時に使える |
| 全員への送信（`Bukkit.getOnlinePlayers` 10 か所、`AudienceUtils` などの一斉送信 27 か所） | サーバーの全員に送る | 部屋の人だけに送る |
| `Bukkit.getPlayer(id)`（`LobbyState`・`DeathmatchState` で多い） | どのスレッドからでも読んでいる | そのプレイヤーを触るのは、部屋のスレッドに限る |
| `Athena.setAllowDisguise(true/false)` | ロビーの間だけ変装を許す、サーバー全体の切り替え | 部屋ごとに状態が違うので、プレイヤーごとに判定する（Athena API に足すか、SG 側で `/disguise` を止める） |
| `ServerStatus`（MOTD の JSON） | サーバー＝1 試合の状況を 1 つ返す。Hub の看板（AthenaHub の `JoinSigns`・`StatusPing`）が読む | 部屋ごとの状況の一覧を返す。Hub の看板も部屋ごとにする |
| `LobbyGc`・`CleanupState` | 試合後にロビーで `System.gc()` を呼ぶ | `Athena.requestGarbageCollection()` に替える（ロビーを待たせない。実機で確かめ済み） |
| `StatsService`（`Object2ObjectOpenHashMap`）、`CombatTracker`・`ArrowLimit`・`ExhaustionScaler`（毎 tick のタスク） | サーバースレッドだけが触る前提 | 戦績は部屋をまたいで共有なので、スレッド安全にする。毎 tick のタスクは部屋ごとに、部屋のスレッドで回す |
| チャット（`AsyncPlayerChatEvent` → サーバースレッドへ移ってから処理） | サーバースレッドに移る | 発言した人の部屋のスレッドへ移る。届く相手もその部屋だけ |
| `Scoreboards` | 全員分を 1 秒ごとにサーバースレッドで描く | 部屋ごとに、部屋のスレッドで描く |
| `static` の可変な状態 | 61 ファイルに `static` が 168 か所（大半は定数）。可変なものは 1 つずつ確かめる | 部屋をまたいで共有されるものは、スレッド安全にするか部屋ごとにする |

## 3. 部屋とスレッドの持ち主

試合中のイベント（ブロックを壊す・殴る・死ぬ・チェストを開ける）は、取り消すかどうかをその場で決める必要があります。サーバースレッドへ回して後から決めることはできません。そのため、**部屋の状態は、その部屋の試合のワールドを持つスレッドだけが触る**、という形にします。

### 部屋のワールドを 1 本のスレッドにまとめる（Athena への追加）

v2 のトーナメントのデスマッチは、試合のマップとは別のワールド（会場）へ移ります。今の Athena はワールド 1 つにスレッド 1 本です。会場のワールドは別のスレッドになり、部屋の状態を 2 本のスレッドが触ることになります。

そこで Athena に、**いくつかのワールドを 1 本のスレッドで回す**機能を足します（例：`Athena.startWorldThread(World first, World... more)` か、`Athena.joinWorldThread(World world, World owner)`）。

- 同じスレッドのワールドどうしの移動は、今と同じくその場で終わる（`athenaSameTickThread` がそのまま使える）。
- 部屋のスレッド＝部屋の試合のマップと会場をまとめて回すスレッド、になります。

### ロビーの間の持ち主

ロビーはサーバースレッドで回るので、ロビーの段階の部屋はサーバースレッドが持ちます。試合が始まると部屋のスレッドへ移り、終わるとサーバースレッドへ戻ります。部屋に「今の持ち主のスレッドで実行する」入口（`room.execute(task)`）を作り、リスナー・コマンド・チャットはすべてそこを通します。

## 4. 決めたこと（2026-11-03、ユーザー）

- 土台は **v2**。部屋ごとに `team-size` を持たせ、ソロの部屋とデュオの部屋を作れるようにする。
- **部屋ごとのロビー**。部屋ごとに今と同じロビーの段階を持ち、Hub の看板で部屋を選ぶ。
- **1 部屋 1 スレッド**。Athena に、いくつかのワールドを 1 本のスレッドで回す機能を足す。
- Hub からは **データベースで渡す**。Hub が「次に入る部屋」を MariaDB に書き、SG がログイン前に読む。

以下は、決める前に挙げた選択肢です。

### 選択肢

1. **土台のブランチ**：v2（`team-size` でソロもデュオも動く。ボーダー・トーナメント・会場を含む）か、main（v1、ソロだけ）か。
2. **部屋とロビーの形**：
   - (a) 部屋ごとに今と同じロビーの段階（投票・チーム作り・カウントダウン）を持たせる。Hub の看板で部屋を選ぶ。今の sg1・sg2 の看板がそのまま部屋になる形。
   - (b) ロビーは共有の待合所にし、人がそろったら部屋を自動で作って送り出す。
3. **部屋ごとにソロとデュオを混ぜるか**（例：部屋 1〜6 はソロ、7〜12 はデュオ）。
4. **Hub から部屋への入り方**：Velocity が送れるのはサーバー単位なので、どの部屋に入るかを別に伝える必要がある。案は、Hub が看板を押した人を MariaDB（戦績と同じデータベース）に「次に入る部屋」として書き、SG がログイン前（`AsyncPlayerPreLoginEvent`、今も戦績を読んでいる所）に読む方法。

### 段階 1 の結果（2026-11-03、SG `feature/rooms`、まだ commit していない）

- `room/Room`（部屋 1 つ分の `Game`・`Arenas`・`Eliminations`・`StateFactoryImpl`・`Scoreboards`・`CombatTracker` と、部屋にいる人）と `room/Rooms`（部屋の一覧と、誰がどの部屋にいるか）を足した。部屋の数は config.yml の `rooms`（既定 1）。
- 入ってきた人は、ロビーで待っている人がいちばん多く、まだ空きのある部屋へ入る（Hub からの指定は段階 4）。
- 試合のワールドの名前は `sg-{部屋}-{マップ}`。2 つの部屋が同じマップを同時に使える。
- 部屋ごとに登録するリスナー：殴り合いの記録・チェスト・火打石・モブ・試合（`GameEventListener`）・ロビー・カウントダウン。ロビーとカウントダウンと試合後のダメージは、その部屋のプレイヤーだけを見るようにした。サーバーで 1 つのままのもの：壊せるブロック・天気・矢の数・釣竿・パンチ・空腹（逃げている人の判定は、その人の部屋の記録に聞く）。
- コマンド（`/records`・`/vote`・`/team`・`/bounty`・`/sponsor`）は、送った人の部屋の試合を見る。ゲームループは 1 本のまま、部屋ごとに 1 秒進める。
- MOTD の状況は、段階 4 までは最初の部屋のもの。
- 単体試験 143 件はすべて通った。手元の 1 試合（`bench/sg_local.py`、run_sg_short の設定、ボット 24 体、Athena は wt-p10、2 CPU・ヒープ 192M）：24 体全員が完走し、ロビー → PreGame → Live → PreDeathmatch → Deathmatch → End のどの段階も 20 TPS、サーバーのエラー 0。試合のワールドは `sg-1-Par_72_Revamped`。

段階 2 で直すこと：状態のクラスの一斉送信（`Bukkit.getOnlinePlayers`・`AudienceUtils`）を部屋の人だけにする、`LobbyState` の入場時の処理と、次の試合へのチームの持ち越しを部屋の人だけにする、`PlayerReset` の見せる・隠すを部屋の中だけにする、チャットを部屋の中だけにする。

### 段階 2 の結果（2026-11-03、SG `feature/rooms`、まだ commit していない）

洗い出してみると、状態のクラスの送信の大半は、もともと試合のプレイヤーと観戦者（`match.players()`・`spectators()`）宛てで、部屋の中に収まっていました。サーバー全体を相手にしていたのは次の箇所で、部屋の中だけにしました。

| 箇所 | 今まで | 変えたこと |
|---|---|---|
| `LobbyState.onEnter` | オンラインの全員を次の試合のプレイヤーにして、持ち物などを戻す | 部屋にいる人だけ |
| 次の試合へのチームの持ち越し（`StateFactoryImpl`） | サーバーにまだいる人 | 部屋にまだいる人 |
| `LiveGameState` のボスバーを消す | オンラインの全員 | 部屋にいる人（段階 3 で、ほかの部屋のスレッドのプレイヤーを触らないためにも要る） |
| 変装の可否（`Athena.setAllowDisguise`） | ロビーの間だけ許す、サーバー全体の切り替え | 切り替えをやめ、`DisguiseGate` が、その人の部屋がロビーでなければ `/disguise`・`/d` を止める |
| `LobbyGc`（試合後の GC） | ロビーで `System.gc()`（呼んだスレッドが待つ） | `Athena.requestGarbageCollection()`（待たない）。増え方の記録は部屋をまたいで 1 つ |

そのままにしたもの：
- 観戦者を見せる・隠す（`PlayerReset`）は全員が相手のまま。部屋が違えばワールドも違うので見え方は変わらず、hide/show は Athena でスレッド安全にしてある。
- `/sponsor` のメニューの更新は、同じ試合のメニューだけを直す。

確かめた結果：
- 単体試験 143 件はすべて通った。
- 手元で、部屋を 2 つにしてボット 48 体を流した（Athena は wt-p10、2 CPU・ヒープ 256M、2 回）。
  - 2 回とも 48 体全員が完走し、どの段階も 20 TPS、サーバーのエラーは 0 件。
  - 2 つの部屋が同じマップを `sg-1-Par_72_Revamped` と `sg-2-Par_72_Revamped` として同時に読み込んだ。
  - anon の最大は 327 MiB（1 部屋・24 体のときは 372 MiB で、ヒープは 192M）。
- この回のボットは 1 試合で抜けるので、試合後の GC の経路は通っていない。

段階 3 で直すこと：ゲームループ・殴り合いの記録・矢の数・空腹は、今はサーバースレッドで全員を回している。これを部屋のスレッドに移す。

### 段階 3 の結果（2026-11-03、SG `feature/rooms`、まだ commit していない）

部屋の状態を触るスレッド（持ち主）を決め、試合の間は部屋を試合のワールドのスレッドで動かすようにしました。

| 箇所 | 変えたこと |
|---|---|
| 持ち主 | ロビーと Cleanup の間はサーバースレッド、PreGame〜EndGame は試合のワールドを回すスレッド。持ち主を替えるのは、今の持ち主が 1 秒の処理を終えたときだけ（`Room#moveToMatchThread`・`moveToServerThread`）。試合のワールドのスレッドは、PreGame に入った 1 秒の処理の最後に作る（PreGame の入り口の処理は、まだサーバースレッドがワールドを持っているうちに済む） |
| ゲームループと毎 tick の処理 | 部屋ごとの毎 tick の処理（`roomTick`）に、1 秒ごとの `game.second()` とスコアボード、殴り合いの記録、空腹、矢の数をまとめた。サーバーのスケジューラ（全部屋）と試合のワールドのタイマー（`Athena.runOnWorldTimer`）の両方から呼び、持ち主のスレッドで呼ばれたほうだけが動く。そのため、ロビーが固まっても試合は進む |
| 空腹・矢の数 | サーバーの全員を回すのをやめ、部屋の毎 tick の処理の中で、今のスレッドのワールドにいる部屋の人を 1 人ずつ（`ExhaustionScaler#tick(Player)`・`ArrowLimit#trim`） |
| 入場・退出・チャット | 部屋の持ち主のスレッドへ回す（`Room#execute`）。試合中の部屋に入った人は、試合のワールドのスレッドで観戦者になる |
| Bukkit のスケジューラで試合中の人を触っていた所（リスポーン、観戦者にする、`/sponsor` のメニューを閉じる、矢を数え直す） | その人のワールドのスレッドで次の tick に（`PlayerThreads#nextTick`） |
| ロビーに入るときの、プレイヤーの状態の戻し | まだ試合のワールドにいる人は、そのワールドのスレッドで（`PlayerThreads#run`） |
| 共有の状態 | 戦績（`StatsService`）は同期、ランクの一覧・釣竿の待ち時間・`/bounty` の確認待ちは `ConcurrentHashMap` |
| 部屋の tick の例外 | その部屋で止めてログに残す（サーバースレッドのループは全部屋を順に回すので、ほかの部屋を飛ばさない） |

確かめた結果（単体試験 143 件はすべて通過）。手元で部屋 2 つ・ボット 48 体・Athena wt-p10・検出器ありで流しました。
- 1 試合ずつの回：48 体全員が完走、どの段階も 20 TPS、エラー 0、検出器 0 件。PreGame から `World thread` の CPU が出ており、部屋が試合のワールドのスレッドで動いていた。
- 2 試合ずつの回（1 回目）：ロビーへ戻るところで例外 2 件（`Asynchronous player tracker update`）。サーバースレッドが、まだ試合のワールドにいた人の状態を戻そうとしていた。この回は 2 試合目のロビーから進まなかった。上の「ロビーに入るときの戻し」で直した。
- 2 試合ずつの回（直した後）：48 体全員が 2 試合を完走、どの段階も 20 TPS、エラー 0、検出器 0 件。2 つの部屋とも 2 試合目を新しいスレッドで回した。試合後の GC の判断（`Old generation 54 / 171 MB`、頼むほどではない）も通った。anon の最大は 367 MiB。

まだ確かめていないこと：1 つの部屋を固まらせたとき、ほかの部屋とロビーが止まらないこと（`sg_local.py` に凍結の手段がない）。段階 5 の実機の試験で確かめる。

### 段階 6 のあとで調べたこと（2026-11-04）

**Shady_Hollow の End に入る tick（原因が分かった）**
- End に入るときの遅さは Shady_Hollow だけで、毎回起きていた（長時間の回で 34 回中、500 ms 超が 18 回、中央値 501 ms、最大 1,683 ms）。ほかの 4 マップは中央値 53〜57 ms、最大 140 ms 以下。
- 手元で JFR を取った（`hubtest.py --map Shady_Hollow --jfr`）。End に入った直後の試合のスレッドは、ほとんどが光の計算だった。
  - 呼び出しの元：`BlockDaylightDetector.updatePower` → `BlockRedstoneTorch.updateTick` → `BlockRedstoneLamp.doPhysics` → `World.checkLight` → `Chunk.initLighting`。
- Shady_Hollow には、日光センサーで点く街灯（レッドストーンランプ）の回路がある。`EndGameState.onEnter` は花火のために時刻を夜にする（`setTime(400000L)`）。そのため、すべての街灯が同じ tick に点灯し、光の計算がまとめて走る。
  - 手元（速い CPU、1 部屋ずつ）では 88 ms で済んだ。VPS-B（2 vCPU を 10 部屋で分ける）では 0.5〜1.7 秒になる。
- これは部屋の作り直しで生じたものではない。v2 の End からある処理なので、今の本番（1 サーバー 1 試合）でも、Shady_Hollow の試合の終わりに同じだけサーバーが止まっているはず。部屋では、止まるのはその部屋だけになった。
- 直し方の案（未着手、どれにするかはユーザーが決める）：
  - 試合のワールドでは、レッドストーンランプの点灯・消灯を止める（`BlockRedstoneEvent` で電流を変えない）。街灯は試合の間、テンプレートの状態のまま。
  - End で時刻を夜にしない。花火が昼の空に上がる。
  - 試合の間も `doDaylightCycle` を止め、End の夜も止めたまま。

**起動直後のロビーの 4 秒（原因は分からないまま）**
- 長時間の回で、起動して 11 秒後、最初の 1 人が入ったときに 1 回だけ起きた。SG のログの「joined room」から、サーバーの「logged in」まで 3 秒止まっていた。
- その 3 秒、サーバースレッドの CPU は 0.39 秒だけで、計算ではなく何かを待っていた。同じ 3 秒、Netty（io_uring）は 1.3 秒ぶん忙しく、C1 が 0.6 秒コンパイルしていた（30 体近くが同時にログインし、初めて動くコードが多いところ）。GC はなかった。
- VPS-B のほかの 3 回（sg2-rooms10・sg3-duo-mixed10 と、段階 5 の 12 部屋の回）と、手元の 4 回では起きていない（最初の 1 人は同じ秒のうちに入った）。
- 見込み：起動直後に初めて動くコードを、ディスクから読んでいた（直前の回のあとで、ページキャッシュから追い出されていた）。確かめるには、本番を止めて起動を何度か繰り返し、JFR か major fault の数を取る必要がある。
- 起動直後はどの部屋もロビーで、試合はまだない。響くのは、起動直後に入る最初の数十人のログインが数秒遅れることだけ。

**本番の sg2 は `v2` ではない**
- 本番の sg2 は `deploy/v2-dmarena-teams`（c8d6c20）で動いている。`v2` に入っていない 13 commit・38 ファイル（+2,256 / −534）がある。
  - デスマッチ会場での試合（`feature/deathmatch-arena-matches`）と、その同時開催（`feature/deathmatch-parallel`）
  - 切断した人の代わりのスケルトン（`feature/disconnect-skeleton`）
  - チームを組むコマンド（`feature/team-create`）
  - 告知と長さの直し（`fix/announce-flowers-durations-v2`）
- `feature/rooms` は `origin/v2`（3279a7f）から作ったので、どれも入っていない。このまま本番に入れると、これらの機能がなくなる。
- 本番の sg1 は v1（ソロ）。部屋の版は v2 の上にあるので、sg1 を置き換えるなら、v1 と v2 の違いも合わせて考える必要がある。

**部屋とスレッドに合わせて直したもの**

| 取り込んだもの | 1 サーバー 1 試合の前提 | 直したこと |
|---|---|---|
| デスマッチ会場のワールド | 名前は "sg-dm-{会場}-{番号}"。ライブゲームの間（同じサーバースレッド）にその場で読み込む | 名前を部屋ごとに（"sg-{部屋}-dm-{会場}-{番号}"）。会場の読み込みと破棄はサーバースレッドでしかできない（Athena の `AsyncCatcher`）。部屋が試合のスレッドにいる間は、サーバースレッドに頼んで読み込み、試合のマップと同じスレッドに入れて（`Athena.joinWorldThread`）から部屋へ渡す（`Arenas#openDeathmatchVenues`）。捨てるのもサーバースレッドで。試合が終わってから届いた会場は捨てる。会場の一覧は、ほかの部屋のスレッドからも読める（`CopyOnWriteArrayList`） |

| 観戦コンパス | 戦っている試合の一覧が static で 1 つ | `DeathmatchState` ごとの一覧に。リスナーはサーバーに 1 つで、使った人の部屋の一覧だけを並べる。ほかの部屋の試合は出ず、移れない |
| 切断のスケルトン（`Disconnects`） | サーバーに 1 つ。切断中の人の名前を static の表に置き、試合が終わると表を空にする | 部屋ごとに 1 つ持ち、1 秒の処理も部屋で回す。名前の表はスレッドをまたいで安全な表にし、空にするのは自分の部屋の分だけ。切断中かどうかとスケルトンの持ち主は、どのスレッドからも読める |
| 戻ってきた人 | 入ってきた場所でそのまま元に戻し、スケルトンの位置へ移す | 入ってくるのはロビー（サーバースレッド）。スケルトンのいる部屋に入れ（Hub でほかの部屋を選んでいても）、先にスケルトンの位置へ移し、着いてから（試合のスレッドで）スケルトンを消して持ち物・体力を戻す。部屋が満員なら、ほかの人と同じく断る |
| 試合の人を毎秒触る処理（ボスバー、範囲の外の警告、雷、組み合わせへの配置など） | 全員が同じスレッド | `InMatchStateBase#present`：オンラインで、切断中でなく、この部屋のスレッドのワールドにいる人だけを触る。戻ってくる途中の人はスケルトンとして、途中から入った観戦者は着いてから扱う |
| 待つ陣営から預かった持ち物 | static の `HashMap` | スレッドをまたいで安全な表に |

直す前に流した回（t1）では、戻ってきた人をロビーにいるうちに試合のスレッドで元に戻そうとして例外になった。その人はロビーに残ったまま試合のプレイヤーに数えられ、ボスバーを出そうとして部屋の 1 秒の処理が失敗し続けた。その部屋はライブゲームから進めなくなった（ほかの部屋は進んだ）。

**実機（VPS-B）、sg2 の設定で 10 部屋（未完）**

- ボットの多くが落ちたあとの数字なので、全員がそろった負荷でのメモリは確かめていない。回線のよいときに流し直す。

**sg7：PR の jar（9f843e9）。不具合が 1 つ見つかった**
- ボットは 240/240 が 2 試合を完走した。時間切れは 0。
- SG のタスクの例外が 3 件あった：`IllegalStateException: Asynchronous player teleport!`（`Arenas.tryUnload` ← `unloadOrKeep` ← `retainDeathmatchVenues`）。抜き出しは `results/vps/sg7-sg2conf10/exception.txt`。
- 原因：
  1. トーナメントの回戦が終わると、使わなくなった会場を捨てる。そこにいる人は、部屋のスレッドで残る会場へ移す。
  2. ただし、回戦の最後の一撃で倒れた人（体力 0）は、teleport が何もせず false を返すので会場に残る。
  3. その人は試合のスレッドで生き返る。そのあと、サーバースレッドで会場を捨てる処理が、その人をロビーへ移そうとする。そのワールドは試合のスレッドで回っているので、例外になる。
- 例外で処理が止まるので、会場のワールドは捨てられず、捨て直す一覧（leftovers）にも載らない。その部屋の次の試合では同じ名前の会場を読めず、少ない会場で戦った（「still loaded; using 1 arena(s)」が 2 回）。
- 直したこと（SG e0f2d4a）：
  - 捨てる会場は、その会場を回すスレッドで 10 tick ごとに残っている人を移す。誰もいなくなってから、サーバースレッドで捨てる。倒れている人は、生き返ってから移す。60 秒たっても空にならなければ、そのまま捨てるのを頼む。
  - `tryUnload` は、ほかのスレッドが回すワールドにいる人には触らない。人が残っていれば捨てずに残し、あとでもう一度捨てる。
