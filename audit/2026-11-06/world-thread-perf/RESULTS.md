# ワールドスレッドの性能候補 O1〜O4 の計測（2026-11-06）

`audit/2026-11-06/world-thread-audit/REPORT.md` の性能候補を、VPS-B（2 vCPU、1 GB）で測った。

## 条件

- デュオ 8 部屋 × 24 人。すべてボットで、マップはランダム。ヒープ 320M、Shenandoah。
- 1 形につき 1 回だけ。同じ形でも最大の遅れは回ごとに大きくぶれる（1.1〜2.9 秒）。
- ボットはチャンクやエンティティの受信処理を持たないので、人の接続の負荷は含まない。
- `gap` は試合のワールドの tick の間隔の、5 秒ごとの最大。CPU は全プロセスのコア数。

| 実行 | 内容 | gap 中央値 | p95 | 最大 | 500 ms 超（60 秒以降） | CPU 中央値 / p95 |
|---|---|---|---|---|---|---|
| `i-metrics` | 修正版 + O1 の計測 | 212 ms | 635 ms | 1,241 ms | 6 / 92 | 0.84 / 1.73 |
| `j-jfr` | 同じ + JFR | 183 ms | 548 ms | 1,089 ms | 3 / 79 | 0.76 / 1.57 |
| `l-stagger` | 部屋の開始を 12 秒ずつずらす試験版 | 172 ms | 477 ms | 1,172 ms | 5 / 95 | 0.67 / 1.66 |
| `k-opt` | ブロック番号の改善（下記） | 72 ms | 117 ms | 168 ms | 0 / 75 | 0.44 / 0.85 |

`k-opt` の試合の中身（当たった数、開けたチェスト、歩いた距離）は、ほかの実行と同じ程度だった。ボットが動かなくなって軽くなったのではない。

## O1：スレッドの時間の内訳

- `-Dathena.threadStats=<file>` で、スレッドごとの工程、CPU 時間、遅れ、tick の長さの分布を記録するようにした（server 0411）。指定しなければ動かない。
- `i-metrics` では、スレッドの時間の 97.5% がワールドの tick で、チャンク I/O の完了は 1.9%、タスクと接続は 0.1%。
- 同じ実行で、tick の時間のうち 56% は CPU を使っていない。JFR で見たワールドスレッドのロック待ちは合計約 0.15 秒なので、待ちのほとんどは CPU の順番待ちと判断した。

## O2：処理予算の共有と開始時刻の分散

- チャンク I/O の完了は全体の 2〜5%、1 tick の最大 145 ms、生成の完了はほぼ 0。この負荷では、グループで予算を共有する効果は小さいので、**入れない**。部屋はデスマッチ以外 1 ワールドで、ワールド数倍の問題も起きにくい。
- 開始をずらすと、同時開始の直後の 1 秒超の遅れは消えた。ただ、試合の途中でほかの遅れが出て、最大はほぼ同じだった（1,172 ms）。実際の部屋は自然にずれるので、**入れない**。

## O3：共通の Random

- CPU のサンプルで `Random` と `AtomicLong` は合計 0.1% ほど。ロック待ちにも出ない。**入れない**。

## O4：小さな確保と待機項目

- `tickConnections` は CPU 0.1%、確保 0.1%。`RedstoneLampQueue.drain` は CPU 0.3%。**入れない**。

## 新しく分かったこと：ボットの経路探索

- `j-jfr` で、`Navigator.plan` が CPU の 48%、確保の 71%。そのうち `CraftWorld.getBlockTypeIdAt` が CPU の 37%、確保の 67%（458 秒で 17 GiB の `BlockPosition`）。
- 試した改善は 3 つ（`k-opt`）。
  - Athena：`getBlockTypeIdAt` が `BlockPosition` を作らない（server 0412）。
  - Athena：`Block.getId` がハッシュを引かず、ブロックの持つ番号を返す（server 0412）。
  - SurvivalGames：`Terrain` が 1 tick の間、ワールドごとにブロックの番号を控える（`perf/terrain-cache`）。
- 3 つの効果は分けて測っていない。

## 再測定：Terrain の時計を直したあと

`k-opt` の `Terrain` は、昼夜の時計（`getFullTime`）でキャッシュを更新していたので、昼夜が止まるワールドでは古い値を返す不具合があった（追補報告 R2）。`System.nanoTime()` に直し、マップを Shady_Hollow に固定して、変更を分けて測った。

| 実行 | Athena の変更 | SG の控え | gap 中央値 | p95 | 最大 | 60 秒以降の最大 | 500 ms 超（60 秒以降） | CPU 中央値 / p95 |
|---|---|---|---|---|---|---|---|---|
| `m-base` | なし | なし | 210 ms | 609 ms | 1,360 ms | 1,329 ms | 8 / 77 | 0.86 / 1.89 |
| `m-athena` | あり | なし | 99 ms | 272 ms | 1,069 ms | 272 ms | 0 / 73 | 0.64 / 1.68 |
| `m-sg` | なし | あり | 79 ms | 198 ms | 686 ms | 274 ms | 0 / 89 | 0.52 / 1.15 |
| `m-both-1` | あり | あり | 73 ms | 160 ms | 347 ms | 173 ms | 0 / 81 | 0.50 / 1.31 |
| `m-both-2` | あり | あり | 75 ms | 207 ms | 578 ms | 207 ms | 0 / 69 | 0.51 / 1.31 |

- 改善は残った。ただし `k-opt` の「最大 168 ms、CPU p95 0.85」より悪い。`k-opt` はマップがランダムで、古いキャッシュの影響も切り分けられないので、代表値には上の表を使う。
- それぞれの変更に効果があり、両方で最も良い。SG の控えのほうが効果が大きい。
- 全部の実行で、16 試合のワールドが最後まで動き、エラーは 0 件。当たった数、開けたチェスト、歩いた距離は同じ程度。
- `m-both` の 2 回以外は 1 回ずつ。人の接続の負荷は含まない。

## 再測定：素手のボットのあと、経路探索とテンプレートの読み込みを直す（2026-11-09）

本番の版（paperclip `90c236c2`、SG `e777cc51`）で JFR を付けて測ると（`p-jfr`）、CPU の内訳は次のとおりだった。

- ボットの判断：32%。そのうち経路探索が 24%。
- チャンク I/O のスレッド：17%。そのうち 16% が `ChunkSection.recalcBlockCounts`。テンプレートのセクションを読み込むたびに、4,096 ブロックを `MemorySegment` 越しに数え直していた。
- 経路探索で `isChunkLoaded` が 6%、`Node`・`PriorityQueue`・ハッシュ表が約 6%。

次の 3 つを直した。

- Athena server 0414：テンプレートのセクションのブロック数を、ストアが一度だけ数えて控える。2 回目からの読み込みは数え直さない。
- SG `perf/bot-search`：経路探索が、点ごとのオブジェクトを作らない。スレッドごとに配列、番号のヒープ、開番地の表を使い回す。同点の扱いは `PriorityQueue` と同じなので、経路は変わらない。
- SG `perf/bot-search`：`Terrain` が、探索 1 回の間に 16 個のチャンクの読み込み状態を控える。

8 部屋 × 24 人（全員ボット）、Shady_Hollow に固定。

| 実行 | 版 | JFR | 遅れ 中央 | 遅れ p95 | 遅れ 最大 | 60 秒以降 p95 / 最大 | CPU 平均 / 最大 | 順番待ち |
|---|---|---|---|---|---|---|---|---|
| `q-base` | 本番 | なし | 84 ms | 207 ms | 727 ms | 166 / 220 ms | 0.65 / 1.94 | 31% |
| `q-new` | 直したあと | なし | 76 ms | 172 ms | 197 ms | 134 / 197 ms | 0.57 / 1.39 | 19% |
| `q-new-jfr` | 直したあと | あり | 78 ms | 157 ms | 227 ms | 149 / 157 ms | 0.61 / 1.37 | 21% |
| `p-jfr` | 本番 | あり | 102 ms | 325 ms | 1,016 ms | 299 / 455 ms | 0.80 / 1.99 | 49% |

- 試合開始時の遅れの山（開始 10 秒後、テンプレートの読み込みと重なる）が 727 ms から 197 ms に下がった。
- `p-jfr` が悪かったのは、主に JFR の負荷とみる。JFR なしの本番の版（`q-base`）は、前回の `n-lobbies`（60 秒以降 p95 160 ms）と同じ程度。
- `q-new-jfr` では、チャンク I/O のスレッドが CPU の約 3%（前は 17%）。経路探索の確保は 0.3%（前は 15.7%）。CPU のサンプルの総数は 23,216 から 15,022 に減った。
- 残りで一番重いのは `Terrain.id`（自分の時間 9.3%）。ブロック番号の控え（256 KB）の読み出しで、キャッシュに乗りきらない。
- 当たった数、開けたチェスト、歩いた距離は、`q-base` と `q-new` で同じ程度。エラーは 0 件（`q-new` の 5 件は AOT キャッシュを作るときの警告）。
- どれも 1 回ずつの計測で、人の接続の負荷は含まない。

## ビット表：歩けるかをセクションごとのビット面で引く（2026-11-10）

`q-new` の残りで一番重かった `Terrain.id`（ブロック番号の 256 KB の控え）を、ビット表に置き換えた。

- Athena `perf/section-reads`（api 0067、server 0415）：`Athena.readSectionTypeIds` は、セクションのブロック番号と版を返す。版は、セクションを作るときの通し番号と `modCount` から作る。版が同じなら、番号は写さない。
- SG `perf/bot-grid`：`Terrain` はセクションごとに、ブロックの種類（通れる、立てる、水、上り下り、半分、危ない。組み合わせは 7 通り）を 3 枚のビット面（`long` 64 個ずつ）で持つ。
  - 1 セクションあたり 1.5 KB で、ワールドのボット全員が同じ表を使う。
  - 版を確かめるのは 50 ms に 1 回だけで、前の控えを引き直していた間隔と同じ。
  - 経路探索（A*）はそのまま。

8 部屋 × 24 人（全員ボット）、Shady_Hollow に固定。`r-base` は今の本番（`q-new` と同じ jar）を同じ日に測り直したもの。

| 実行 | 版 | JFR | 遅れ 中央 | 遅れ p95 | 遅れ 最大 | 60 秒以降 p95 / 最大 | CPU 平均 / 最大 | 順番待ち | RSS 最大 |
|---|---|---|---|---|---|---|---|---|---|
| `r-base` | 今の本番 | なし | 77 ms | 141 ms | 184 ms | 141 / 147 ms | 0.54 / 1.87 | 17.6% | 508 MiB |
| `r-grid` | ビット表 | なし | 69 ms | 119 ms | 358 ms | 93 / 138 ms | 0.53 / 1.25 | 14.4% | 507 MiB |
| `r-grid-jfr` | ビット表 | あり | 73 ms | 120 ms | 270 ms | 115 / 157 ms | 0.54 / 1.40 | 15.4% | 498 MiB |

- 試合中（60 秒以降）の遅れの p95 が 141 ms から 93 ms に下がった。ワールドのスレッドの CPU 時間の合計は 166.9 秒から 145.8 秒（13% 減）。
- CPU の平均は変わらない（0.54 と 0.53）。最大は 1.87 から 1.25 コアに下がった。
- `r-grid` の遅れの最大 358 ms は、開始 10 秒後の部屋 3 の 1 回だけ。JFR ありの回も、開始直後に 270 ms が出た。
  - 試合の始めに、全員がまだ読んでいないセクションを一斉に読むためかもしれない。
  - 1 回ずつの計測なので、ぶれとは見分けていない。
- JFR（`q-new-jfr` と `r-grid-jfr`）では、次のように減った。

  | | `q-new-jfr` | `r-grid-jfr` |
  |---|---|---|
  | 全サンプル | 15,022 | 11,614 |
  | `Navigator.plan` | 約 3,680 | 約 2,530（31% 減） |
  | `Terrain.standable` | 約 2,070 | 約 920（56% 減） |

  `CraftWorld.getBlockTypeIdAt`（5.2%）は、内訳から消えた。
- 残りのボットの処理で大きいのは、ボットの体の動き（`AthenaBotPlayer.move` 22.6%、`Entity.move` と当たり判定）。その次が経路探索の残り（A* の点の出し入れ、21.8% から上の分を引いた分）と、スコアボード（5.4%、確保の 14.9%）。
- メモリは増えていない（RSS 最大 508 MiB と 507 MiB）。
- 当たった数、開けたチェスト、歩いた距離の合計は、`r-base` と同じ程度。エラーは 0 件（`r-grid` の 4 件は AOT キャッシュを作るときの警告）。
