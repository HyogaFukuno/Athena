# ワールドごとのスレッドの試験の道具（段階 0）

計画は [`../WORLD-THREADS-PLAN.md`](../WORLD-THREADS-PLAN.md) です。

## 中身

- `plugin/`：試験用のプラグイン `WorldThreadsProbe`。コンソールの `wt` コマンドで操作します。
  - `wt create <n>`：平らなワールド `wt-0`〜`wt-<n-1>` を作る
  - `wt spawn <world> <n>`：豚を出す（AI の負荷）
  - `wt distribute`：オンラインのプレイヤーを各ワールドに振り分ける
  - `wt shuffle <間隔 tick> <秒>`：間隔ごとに、4 人に 1 人を別のワールドへ移す
  - `wt freeze <world> <ms>`：そのワールドを tick しているスレッドを止める。今は `Server thread` なので、全ワールドが止まる
  - `wt status`・`wt dump`
  - 自分のスレッドから 100 ms ごとに各ワールドの full time を `ticks.csv` に書く。イベントがどのスレッドから来たかを `threads.csv` に書く
- `plugin/build.sh <出力 jar>`：このチェックアウトの `PandaSpigot-API` に対してプラグインを組み立てる
- `run_wt.py`：手元でサーバーを起動し（`run/wt`、git の対象外）、ボットを入れて、次の筋書きを流して集計する
  1. ワールドを作り、ボットを振り分ける
  2. `wt-0` を凍らせる
  3. ボットをワールド間で動かし続ける
  4. その途中で `wt-1` を凍らせる

## 使い方

```bash
./gradlew build -x test && ./gradlew paperclipJar   # base/mc-dev と cache/ が要る（本体のチェックアウトからコピー）
python3 audit/2026-11-02/world-threads/run_wt.py --tag base
```

結果は `run/wt-out/report.json` に出ます。

## 基準（2026-11-02、専用のスレッドなし、ボット 12・ワールド 4・豚 30）

| 項目 | 値 |

| `wt-0`・`wt-1` を 5 秒凍らせたときの各ワールドの tick/s | 全ワールドが 0.0（同じ `Server thread` で tick しているため） |
| ボットの時刻の更新の途切れ | 凍結中に最大 6.0 秒、凍結の外では 0 回 |
| ワールドの移動（respawn） | 190 回、失ったボット 0 |
| サーバーのエラーと警告（起動後） | 0・0 |
| イベントのスレッド | すべて `Server thread` |

段階 2 以降の合格の条件：凍らせたワールドだけが 0 で、他のワールドは約 20 tick/s のまま。凍結の外の途切れが 0 回で、失ったボットも 0。

## 段階 1 のあと（server 0387、2026-11-02）

tick の途中で使う static を、スレッドごとかワールドごとの持ち物に移しました。動きはまだ 1 本のスレッドのままです。

- 試験の道具の結果は基準と同じでした。凍結中は全ワールドが 0 tick/s、凍結の外の途切れは 0 回、失ったボットは 0、エラーは 0。
- 単体試験 5,645 件もすべて通りました。
- この道具では、ダメージ・エンチャント・ディスペンサー・苗木の処理は通りません。これらは機械的な置き換えと単体試験で確かめています。

## 段階 2 のあと（server 0388・api 0054、2026-11-02）

選んだワールドを専用のスレッド（`AthenaWorldThread`）で tick できるようにしました。始めるのは `Athena.startWorldThread(world)`、止めるのは `stopWorldThread` です。プレイヤーがいるワールドはまだ対象外です。

`run_wt.py --threaded` の筋書き：テスト用ワールド 4 つを専用のスレッドで回し、ボット 12 体は `world` に置いたまま、次の順に凍らせます。

| 凍らせたもの | world | wt-0 | wt-1 | wt-2 | wt-3 |
|---|---|---|---|---|---|
| wt-0 のスレッド 5 秒 | 20.9 | **0.0** | 20.7 | 20.9 | 20.9 |
| サーバースレッド 5 秒 | **0.0** | 20.4 | 20.2 | 20.2 | 20.4 |
| wt-1 をサーバースレッドに戻してから、サーバースレッド 5 秒 | **0.0** | 20.2 | **0.0** | 20.4 | 20.4 |

（数字は凍結中の tick/s）

- 凍らせたスレッドのワールドだけが止まり、他は約 20 tick/s のままでした。
- 各ワールドの豚 30 匹は、それぞれのスレッドで tick していました。追加と状態の読み出しも、`Athena.runOnWorld` でそのスレッドで行いました。
- エラーと警告は 0 でした。停止時は、全ワールドがサーバースレッドに戻ってから保存されました。
- スレッドなしの筋書き（`run_wt.py`）は、基準と同じ結果でした。単体試験 5,645 件もすべて通りました。

## 段階 3 のあと（server 0389・api 0055、2026-11-02）

プレイヤーがいるワールドも、専用のスレッドに移せるようにしました。プレイヤーの次の処理は、そのワールドのスレッドで動きます。

- パケット
- 接続の tick（キープアライブ・放置のキック）
- コマンド
- チャットの同期の処理
- 退出

あわせて、次の 3 つも変えました。

- イベントは、全体で 1 つのロックの中では呼ばなくなりました。
- チャンクの読み込みと形づくりの完了処理は、そのワールドのスレッドで行います。
- 専用スレッドのワールドの装飾は、そのスレッドで、装飾用のロックを取って行います。

`run_wt.py --players-threaded` の筋書き：ボット 12 体を wt-0〜3 に振り分けてから、4 つのワールドを専用のスレッドに移します。

| 確かめたこと | 結果 |
|---|---|
| wt-0 のスレッドを 5 秒凍らせる | 止まったのは wt-0 だけ。時刻の更新が途切れたボットは wt-0 の 3 体だけ |
| サーバースレッドを 5 秒凍らせる | テスト用ワールドは 20 tick/s のまま。途切れたボットは 0 |
| ボットのコマンド `/wtping` | 12 件すべて、そのボットのワールドのスレッドで実行 |
| ボット 6 体の切断 | 退出の処理 6 件すべて、そのワールドのスレッドで実行。失ったボット 0 |
| ボットの移動のイベント | それぞれのワールドのスレッドから届いた |

スレッドなしの筋書きと、`--threaded` の筋書きの結果も変わりませんでした。単体試験 5,645 件もすべて通りました。

途中で見つけて直したこと：時刻の更新を「サーバー全体の tick 数」で間引いていたため、サーバースレッドが止まると、専用スレッドのワールドのプレイヤーにも時刻の更新が届かなくなっていました。ワールドの tick 数で間引くように直しました。

## 段階 4 のあと（server 0390・api 0056、2026-11-02）

プレイヤーが、tick しているスレッドの違うワールドの間を移れるようにしました。移動は 2 段階で受け渡します。

1. 元のワールドのスレッドで、プレイヤーをワールドから外す。
2. 行き先のワールドのスレッドで、ワールドに入れる。

- 移動の途中でも、プレイヤーはサーバーのプレイヤー一覧に残ります。途中で届いたパケットは、プレイヤーを追って行き先のスレッドで処理されます。
- 移動の途中のプレイヤーを、もう一度テレポートすることはできません（`teleport` は false を返します）。
- 専用スレッドのワールドを狙ったログインは、いったん既定のワールドに入ってから、そのワールドへ受け渡します。
- 復活の行き先も自由になりました。
- プレイヤー側の時計（AthenaGuard の猶予、アイテムを落とす間隔など）は、ワールドを移っても連続するように補正します。
- `teleportAsync`・`teleportGradually`・`preloadChunks` は、どのスレッドからでも呼べます。処理は、それぞれの持ち主のスレッドで行います。

`run_wt.py --moves` の筋書き：4 つのテスト用ワールドを最初から専用のスレッドで回します。そのうえで、ボット 12 体を、既定のワールドを含む 5 つのワールドの間で 30 秒間動かし続けます（`Athena.teleportAsync`）。その途中で次のことを行います。

- wt-0 を 5 秒凍らせる
- 4 体を倒して復活させる
- 2 体を、wt-2 を狙ってログインさせる

| 確かめたこと | 結果 |
|---|---|
| ワールド間の移動 | 165 回、断られた 0、失ったボット 0 |
| wt-0 の凍結 | 止まったのは wt-0 だけ。凍結の外の途切れ 0 |
| 倒して復活 | 4 体とも復活 |
| wt-2 を狙ったログイン | 2 体とも、既定のワールドから wt-2 のスレッドで到着 |
| 新しいワールドに着いたことを知らせるイベント | すべて、そのワールドを tick しているスレッドで発生（外れ 0） |
| 最後の整合性の確認 | オンライン 14、どのワールドにもいない 0、2 つのワールドにいる 0、オンラインでないのに残っている 0 |
| サーバースレッドからの preload（wt-3） | wt-3 のスレッドで完了（平らな新しいワールドで、ディスクにあるチャンクがないため 0 件） |
| wt-1 のスレッドからの段階的なテレポート | 1 体を既定のワールドへ移し、完了の通知はサーバースレッド |

ほかの 3 つの筋書きの結果も変わりませんでした。単体試験 5,645 件もすべて通りました。

## 段階 5 のあと（server 0391・api 0057、2026-11-02）

- **停滞の見張り**：ウォッチドッグが、専用スレッドのワールドを 1 秒ごとに見ます。`worldThreadStallSeconds`（athena.yml、既定 10 秒）の間 tick を終えていないワールドがあれば、次のことをします。この間も、サーバーと他のワールドは止まりません。
  - そのスレッドのスタックをログに出す
  - `WorldThreadStallEvent`（非同期）を出す
  - tick が戻ったら、回復したことも同じイベントで知らせる
- **例外の切り離し**：tick で例外が出たら、そのワールドのスレッドだけが止まります。サーバースレッドがワールドを引き取って止めたまま（halted）にし、次の順に処理します。
  1. `WorldThreadFailureEvent` を出す
  2. まだ残っているプレイヤーを、既定のワールドのスポーンへ逃がす
- **スコアボード**：スコアボードの一覧と、死亡数・キル数・体力による得点の更新を、1 つのロックで守ります。
- **Athena API**：マスク・変装・ボスバーは、プレイヤーを持つスレッドで判定します。変装の登録し直しは、見ている側のスレッドで行います。
- **プレイヤーの保存**：オートセーブでのプレイヤーの保存は、そのプレイヤーを持つスレッドで行います。

`run_wt.py --failures` の筋書き：ボット 12 体を 4 つのワールドに振り分けて専用スレッドに移し、停滞とみなすまでの時間を 2 秒にします。

| 確かめたこと | 結果 |
|---|---|
| wt-0 を 4 秒凍らせる | 2.4 秒で停滞を報告（スタックつき）、`WorldThreadStallEvent`。凍結が解けたあと、3.4 秒の停滞から回復したことを報告 |
| wt-1 の tick で例外を起こす | wt-1 だけが止まり（0 tick/s）、`WorldThreadFailureEvent` がサーバースレッドで発生。中の 3 体は既定のワールドへ移り、失ったボット 0 |
| 例外のあとの他のワールド | world・wt-0・wt-2・wt-3 は約 21 tick/s のまま |
| 整合性の確認 | オンライン 12、どのワールドにもいない 0、2 つのワールドにいる 0、オンラインでないのに残っている 0 |
| ログ | エラーと警告は、意図して起こした停滞と例外の 4 件だけ |

ほかの 4 つの筋書きの結果も変わりませんでした。単体試験 5,645 件もすべて通りました。

## 段階 6：競合の試験とベンチ（server 0392・api 0058、2026-11-02）

### 足したもの

- **`Athena.runOnWorldTimer(world, task, delay, period)`**：ワールドを tick しているスレッドで、そのワールドの tick の始めに回る定期タスク（`WorldTask` で取り消す。ワールドを捨てると止まる）。サーバースレッドの Bukkit スケジューラに当たるもので、専用スレッドの試合の時計（カウントダウン・状態の移り変わり）はここで回す。サーバースレッドや他のワールドが止まっても遅れない。作り直す SG もこれを使う。
- **不正なスレッドの検出器**：`-Dathena.threadCheck=true` で、ブロックの変更、エンティティの追加・削除・kill・移動、チャンクの読み込みと参照、エンティティトラッカー、プレイヤーのチャンクマップ、`AsyncCatcher` が断った呼び出しを、ワールドを tick していないスレッドから呼ばれたら記録する。場所ごとに 1 回スタックを出して数え、サーバーの停止時に一覧を出す。既定では定数の false なので、JIT で消える。
- **`matchsim/`**：SG の代わりの試合プラグイン（Bukkit と Athena API だけ）。SG と同じ流れを、同時に複数回す。
  - ロビーで 24 人そろったらカウントダウン
  - テンプレートのマップを読み込み、試合の範囲（半径 300）とデスマッチ会場を固定して事前に読み込む
  - 4 人ずつテレポート
  - 準備 15 秒 → 本戦 300 秒 → デスマッチ前 30 秒 → デスマッチ 120 秒 → 終了 15 秒 → 後片付け 5 秒
  - チェストは開けたときに中身を入れる。PvP で倒れたら持ち物を落とし、隠れて飛ぶ観戦者になる
  - プレイヤーごとのサイドバー（変わった行だけ送る）
  - 後片付けでロビーへ戻し、マップを捨て、1 秒後に `System.gc()`
  - チャットの文言は sgbot.py が読むもの
  - 試合の時計は `runOnWorldTimer`（本体の jar では Bukkit スケジューラ）。`threaded: true` で各試合のワールドを専用スレッドへ
  - 各ワールドが自分のスレッドで、20 tick ごとに tick の間隔（最大、60 ms 超・100 ms 超の数）を `ticks.csv` に書く
- **`sim_local.py`**：colima の athena VM の中で、cgroup で制限したコンテナにサーバーを起動し、ボット（`sgbot.py`、本体の bench からコピー）を流して集計する。
  - CPU 2・メモリ 3g、本番の JVM フラグ（`start-small.sh` の C1 だけ・Parallel GC など。AOT キャッシュはなし）
  - 本番の設定（ArcanaServers `vps-b/sg1`：view distance 8、io_uring など）を、ベンチに要るところだけ変える：プロキシなし、接続の制限なし、飛行を許す、guard を切る（ボットが飛ぶため）、max-players をボット数に
  - `--freeze 秒:試合:ms` で、試合（`m2` なら今動いている 2 番目）かロビーのスレッドを止め、その間に各ワールドが何 tick 進んだかを出す
- **`series_p6.sh`**：下の表の回を順に流す。

本体は、このブランチの分かれ目の 33809d3（server 0386）の jar です（`~/athena-bench-work/base386` でビルド）。マップは Lobby_Games、ボットは 1 体 3 試合（同じ JVM で続けて）です。

### 結果

| 回 | jar | 同時の試合 | スレッド | ヒープ | ボット | anon のピーク | GC 後のヒープの最大 | 60 ms 超の tick | 100 ms 超 | 戦っている間の CPU |
|---|---|---|---|---|---|---|---|---|---|---|
| p6-base-1 | 本体 | 1 | — | 128M | 24/24 | 203 MiB | 67 MB | 54（0.19%） | 1 | 0.094 コア |
| p6-wt-1 | ブランチ | 1 | なし | 128M | 24/24 | 184 MiB | 48 MB | 34（0.13%） | 0 | 0.090 コア |
| p6-wt-2t | ブランチ | 2 | あり | 256M | 48/48 | 245 MiB | 63 MB | 15（0.03%） | 1 ※ | 0.135 コア |
| p6-wt-3t | ブランチ | 3 | あり | 384M | 72/72 | 305 MiB | 79 MB | 22（0.03%） | 1 ※ | 0.145 コア |
| p6-wt-3 | ブランチ | 3 | なし | 384M | 72/72 | 305 MiB | 80 MB | 43（0.05%） | 1 | 0.123 コア |
| p6-wt-3t-192 | ブランチ | 3 | あり | 192M | 72/72 | **233 MiB** | 73 MB | 18（0.02%） | 0 | 0.145 コア |

※ 意図して凍らせた 1 回（5 秒）。「戦っている間」は、すべての試合が本戦〜デスマッチにいた時間です。

- **メモリ**：1 つの JVM に試合を足すと、1 試合あたり約 60 MiB 増えるだけです（184 → 245 → 305 MiB）。本体で 1 試合ずつ別の JVM にすると 203 MiB ずつ要るので、3 試合なら約 609 MiB です。1 つの JVM なら 305 MiB で、約半分です。
- **スレッドの費用**：3 試合同時でスレッドあり・なしを比べると、メモリは同じ（305 MiB）、CPU は少し増え（0.123 → 0.145 コア）、遅れた tick は少し減りました（0.05% → 0.03%）。この CPU（Mac の M 系）では 1 本のスレッドでも間に合っているので、スレッドの効果は「1 つの試合が固まっても他が止まらない」ことのほうです。
- **ヒープ**：3 試合同時でも GC 後に残るのは 80 MB ほどでした。試合数×128M は大きすぎます。ヒープを 192M にしても、遅れた tick は増えず（0.02%、100 ms 超 0）、anon は 233 MiB に下がりました。3 台に分けた場合（約 609 MiB）の約 38% です。代わりに GC の回数は 74 → 140 回に増えました（最長の停止は 49 → 54 ms で、ほぼ同じ）。
- **ブランチ自体の退行**：1 試合でスレッドなしのブランチは、本体と比べて悪くなっていません（anon 184 対 203 MiB、遅れた tick 0.13% 対 0.19%）。

### 競合の試験

- **p6-wt-3t-race**：3 試合同時、スレッドあり、検出器あり。各ボット 6 試合（本戦 120 秒・デスマッチ 60 秒にして、試合の読み込み・捨てる・ワールド間の移動を多く回す）。
  - 試合を 18 回読み込んで捨て、ボット 72 体が全員 6 試合を終えた。失ったボット 0、タイムアウト 0
  - **不正なスレッドからの呼び出し 0 件**、サーバーの警告・エラー 0
  - 凍結は 2 回が効いた。試合 1 を 4 秒止める → 試合 1 だけ 0 tick/s、他の 2 試合とロビーは 20 tick/s。ロビー（サーバースレッド）を 4 秒止める → 3 試合とも 20 tick/s
  - 残りの 2 回は、狙った試合がもう終わっていて何も起きなかった（試合の番号で指定したため）。次の回で測り直した
- **p6-wt-3t-freeze**：今動いている試合を順番で指定して、測り直した。3 試合同時、各ボット 2 試合、検出器あり。

| 凍結 | 止めたワールド | 止まったもの | 他 |
|---|---|---|---|
| m1 を 4 秒 | sg-lobby_games-1 | そのワールドだけ 0 tick/s | 他の 2 試合とロビーは 20 tick/s |
| m2 を 12 秒 | sg-lobby_games-2 | そのワールドだけ 0 tick/s。10.9 秒で見張りが停滞を報告（スタックつき）し、11.9 秒で回復を報告 | 他の 2 試合とロビーは 20 tick/s |
| ロビーを 4 秒 | サーバースレッド | ロビーだけ 0 tick/s | 2 試合とも 20 tick/s |
| m3 を 3 秒 | sg-lobby_games-6 | そのワールドだけ 0 tick/s | 他の 2 試合とロビーは 20 tick/s |

不正なスレッドからの呼び出しは 0 件、警告・エラーは見張りの 2 行だけ、失ったボットは 0 でした。

### 注意

- CPU の数値は Mac（M 系）の上の VM です。ConoHa の vCPU はずっと遅いので、CPU の絶対値はそのまま当てはまりません。比べるのは同じ条件の回どうしです。
- AOT キャッシュとロビーの GC の設定がないので、本体の 1 試合の anon（203 MiB）は本番の計測（172〜177 MB）より大きく出ています。こちらも比べるのは回どうしです。
- ボットは飛ぶので、バニラの「moved wrongly」の警告が出ます（どの回も同じくらい）。集計からは外しています。
