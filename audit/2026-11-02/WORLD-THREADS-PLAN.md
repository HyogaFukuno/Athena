# ワールドごとに独立した tick ループ — 書き換えの洗い出しと計画（2026-11-02）

対象は Athena 単体です（SurvivalGames は対象外）。ブランチは `feature/world-threads` で、`fix/review-2026-11-01`（server 0386 まで）から切りました。この文書はソースを読んだ結果で、まだ何も書き換えていません。行番号は `PandaSpigot-Server` の 0386 時点のものです。

## 1. 目標と方針

- 選んだワールド 1 つにつき専用のスレッドを 1 本持たせ、そのスレッドが自分の 50 ms ループで tick する。
- ワールドのスレッドが止まっても、他のワールドのスレッドと全体のスレッドは動き続ける。
- **既定では今と同じ動作にする。** 専用のスレッドを持つのは、設定または API で指定したワールドだけ。指定しなければ、全ワールドが今と同じく `Server thread` で tick する。これで、本番の動作を変えずに少しずつ移せる。
- 防げないもの：GC の停止（全スレッドが止まる）、メモリ不足、JVM のクラッシュ。

## 2. スレッドの役割

| スレッド | 受け持つもの |
|---|---|
| 全体のスレッド（今の `Server thread`） | 接続の受け付けとログイン、`PlayerList` への出入り、コンソールのコマンド、Bukkit のスケジューラ、ワールドの作成と破棄、オートセーブの指示、サーバーの ping、`ServerTickStart/EndEvent`、専用のスレッドを持たないワールドの tick |
| ワールドのスレッド（ワールドごとに 1 本） | そのワールドの `doTick`・`tickEntities`・tracker、そのワールドにいるプレイヤーのパケットの処理と `PlayerConnection.c()`、そのワールドのチャンクの読み込みの完了処理、preload と段階的なテレポートのうちそのワールドの分、そのワールド用のタスクの列 |

「スレッドの持ち主」の判定を 1 か所にまとめます：`WorldServer.isOwnedByCurrentThread()` と、`Athena` のスレッド判定ヘルパー（全体のスレッドかどうか、指定したワールドのスレッドかどうか）。

### 3.7 Athena API に足すもの

- `World` ごとのスレッドを有効にする：`Athena.setWorldThreaded(World, boolean)`。`athena.yml` の、ワールド名のパターンでの指定もできるようにする。
- `Athena.isWorldThread(World)`：今のスレッドが、そのワールドを持っているか。
- `Athena.runOnWorld(World, Runnable)`、遅延・繰り返しの版：ワールドのスレッドで実行する。
- `Athena.teleportAsync(Player, Location)`：ワールドをまたぐ移動。終わったら通知する。
- ワールドが止まった・tick で例外が出たことを知らせるイベント。

## 5. 危ういところ

- **プラグインの前提**：プラグインは「イベントはすべて 1 本のスレッドで来る」と考えて書かれている。§3.5 でイベントのロックを外すと、SurvivalGames や FastBoard などで、共有のデータに複数のスレッドから触る箇所が問題になる。Athena 単体の段階では、試験用のプラグインだけで確かめる。
- **ワールドをまたぐ処理**：受け渡しの途中で切断された、移動中に死んだ、移動中にもう一度移動を頼まれた、などの組み合わせが多い。段階 4 で、試験の場面として全部を作る。
- **1 本のスレッドの前提で書かれた Athena の最適化**：送信のまとめ（`athenaBatchThread`）、パケットのキャッシュ、テンプレートの共有。どれも、どのスレッドから触るかを確かめ直す。
- **CPU の数**：本番の箱は 2 vCPU。ワールドのスレッドが増えても、実際に並列に動くのは 2 本まで。それでも、1 つのワールドが固まったときに他が影響を受けないという効果は残る。

### 残っている制約（段階 7 のあと）

- **既定のワールド**（`worlds.get(0)`）は、専用のスレッドにできない。ログインと復活の受け皿のため（§7 で、設計として残すと決めた）。
- **一度例外で止まったワールド**は、もう一度スレッドを持てない（破棄して作り直す）。
- **Timings** は、最初のワールドのスレッドを始めたときに止まる。
- **バニラのコマンド**は、専用スレッドのワールドがある間は、全ワールドのスレッドを止めてサーバースレッドで動く。プレイヤーが打ったものは 1 tick ほど遅れて動き、専用スレッドのワールドのコマンドブロックは成功数が 0 になる。固まっているワールドがあると、5 秒待って実行しない。
- **別のスレッドのワールドにあるベッド**には復活しない（既定のワールドのスポーンに復活する）。
- **プレイヤー以外のエンティティ**がスレッドの違うワールドへ移るとき、乗っているもの・乗せているもの・リードは付いてこない。移り先が着く前に捨てられたら、エンティティは消える。
- **Bukkit の `World` の操作**（`setTime` など）を、そのワールドを持たないスレッドから呼ぶのは、今までどおりプラグインの責任（`Athena.runOnWorld` を使う）。

## 7. 残っている制約を減らす（段階 7、2026-11-02 に洗い出し）

§6 の制約を 1 つずつ調べ、直すものと、設計として残すものに分けました。

### 直すもの

| 制約 | 調べて分かったこと | 直し方 |
|---|---|---|
| **バニラのコマンド**（`/time`・`/weather`・`/gamerule`・`/tp` など） | `VanillaCommandWrapper.dispatchVanillaCommand`（とコマンドブロックの `CommandBlockListenerAbstract`）は、実行のたびに、サーバー全体で共有している `MinecraftServer.worldServer` 配列を「送り主のワールドを先頭にした全ワールド」に差し替え、終わったら戻す。`/time` はその全ワールドの時刻を、`/save-all` は全ワールドを書き換える。セレクター（`@a`・`@e`）も全ワールドを探す。プレイヤーのコマンドはそのプレイヤーのワールドのスレッドで動くので、2 つのスレッドが同時に実行すると配列の差し替えが壊れ、他のスレッドのワールドを触る | バニラのコマンドは、サーバースレッドが**全ワールドのスレッドを tick の境目で止めた状態で**実行する（排他の区間）。ワールドのスレッドで打たれたものはサーバースレッドへ回す（結果のメッセージは 1 tick ほど遅れる）。止まらないワールド（固まっている）があれば、待つのは数秒までで、コマンドは実行せずに送り主へ知らせる。コマンドブロックも同じ（専用スレッドのワールドでは、成功数は 0 として扱う） |
| **`hidePlayer`・`showPlayer`** | 隠す相手の記録（`hiddenPlayers`）は普通の `HashSet` で、見る側のワールドのトラッカーがそのスレッドで読む。呼んだスレッドで、見る側のワールドのトラッカー（`EntityTrackerEntry.clear`・`updatePlayer`）をじかに触る。SG は観戦者を「オンラインの全員」から隠すので、別のスレッドのワールドにいる人も触る | 記録をスレッド安全な集合にし、すぐに反映する。トラッカーとパケットの処理は、見る側のプレイヤーのワールドのスレッドへ回す（`athenaRunForEntity`。同じスレッドなら今まで通りその場で） |
| **プレイヤー以外のエンティティのワールド間の移動** | `Entity.teleportTo`（ポータル、`CraftEntity.teleport`）は、元のワールドから消して、移り先のワールドに新しいエンティティを作って足す。両方のワールドを 1 つのスレッドで触るので、スレッドが違うワールドの間では断っていた | プレイヤーと同じ 2 段階にする。元のスレッドで NBT に書き出して消し、移り先のスレッドで作り直して足し、Bukkit の `Entity` をつなぎ替える。`teleport` は着く前に返る |
| **プラグイン側のスコアボード** | NMS の `Scoreboard`・`ScoreboardServer` は `HashMap` だけで守りがない。メインのスコアボード（チーム・名前の下の表示）は全ワールドで 1 つなので、プラグインが複数のスレッドから変えると壊れる。一覧を返すメソッドは中身そのもの（view）を返す | 1 つのスコアボードの操作を、そのスコアボードのロックで守る（NMS の `Scoreboard`・`ScoreboardServer` のメソッドを `synchronized` にし、得点やチームの変更も同じロックで）。一覧はコピーを返す |

### 設計として残すもの

| 制約 | 残す理由 |
|---|---|
| **既定のワールドは専用のスレッドにできない** | ログインと復活の受け皿、プレイヤーリスト、オートセーブ、コンソールのコマンドがサーバースレッドを前提にしている。ロビーをサーバースレッドで回し、試合のワールドを専用スレッドにする形（SG の作り直しの想定）で困らない |

## 8. ロビーの遅れ（2026-11-03 に洗い出し）

### 調べて分かったこと

VPS-B の実機の計測（`world-threads/README.md` の「実機の計測」）で、ロビー（サーバースレッド）の tick が 300〜1000 ms 止まることがありました。ロビーで 150 ms を超えた遅れを、試合のワールドを捨てた時刻と突き合わせた結果です。

| 回 | ロビーの 150 ms 超 | そのうち、試合を捨てた 4 秒以内 |
|---|---|---|
| ParallelGC 8 試合、試合後の System.gc あり | 14 | 14 |
| ParallelGC 8 試合、試合後の System.gc なし | 3 | 0 |
| Shenandoah 12 試合、System.gc あり | 30 | 26 |

- 試合のワールドの読み込み（`Match N loaded in 18〜49 ms`）と、ワールドを捨てる処理（`unloadWorld`）は軽い。
- 遅れの元は、捨てた 1 秒後に**サーバースレッドが呼ぶ `System.gc()`** でした。
  - ParallelGC では、Full GC が全スレッドを止める。
  - Shenandoah・ZGC に `-XX:+ExplicitGCInvokesConcurrent` をつけると、他のスレッドは止まらない。ただし `System.gc()` は並行のサイクルが終わるまで**呼んだスレッドを待たせる**（300〜600 ms）。つまりロビーだけが止まる。

### 直し方

| 場所 | 変更 |
|---|---|
| API `athena.api.Athena` / `AthenaServer` | `requestGarbageCollection()` を足す。tick のスレッドを待たせずに GC を頼む。 |
| サーバー `athena.server.AthenaGcRequests`（新規） | 専用のデーモンスレッド（`Athena GC request`）で `System.gc()` を呼ぶ。動いている間に来た頼みは、終わったあとの 1 回にまとめる。動いている最中のサイクルは、その間に手放されたマップを拾えないので、1 回は回し直す。 |
| サーバー `AthenaServerImpl` | 上をつなぐ。 |
| 単体試験 `AthenaGcRequestsTest` | 呼んだ側が待たされないこと、続けて頼んでも回数がまとまること。 |
| MatchSim | 試合後の `System.gc()` を、あれば `Athena.requestGarbageCollection()` に替える（ない jar では今まで通り）。 |

### 確かめ方

VPS-B で、Shenandoah 320M・12 試合の回（v5-shen320-12m）と同じ条件で流し、ロビーの遅れと試合の tick を比べる。

### 結果（2026-11-03）

server 0394・api 0060。単体試験はすべて通りました（`AthenaGcRequestsTest` の 2 件を足した）。

VPS-B で、Shenandoah 320M・12 試合（ボット 288 体）を、直す前の回（v5）と同じ条件で流しました（v9）。MatchSim は `GC requests true` で起動し、試合後の GC を `Athena.requestGarbageCollection()` に替えています。

| | 直す前（v5） | 直した後（v9） |
|---|---|---|
| ロビーの最悪の tick | 622 ms | **284 ms** |
| ロビーの 150 ms 超 | 30 回（うち試合を捨てた直後 26） | **11 回（うち 7）** |
| ロビーの 60 ms 超 | 173 | 156 |
| 試合の最悪の tick | 156 ms | 192 ms |
| 試合の 100 ms 超 | 118 | 118 |
| 試合の 60 ms 超 | 0.55% | 0.69% |
| RSS / 箱の空きの最小 | 495 / 149 MiB | 493 / 125 MiB |

- **ロビーの大きな遅れは消えました。** 試合後の GC で、サーバースレッドが 300〜600 ms 待たされることはなくなりました。
- **残った 150〜284 ms の遅れ**は、試合を終えた 24 人がまとめてロビーへ戻る時刻、または並行の GC が 2 vCPU を使っている間に起きています。待ちではなく、CPU の取り合いです。
- **試合の 60 ms 超が少し増えた分（0.55 → 0.69%）**も同じ理由です。sshd がこの回は 0.36 コアと多く、回ごとのばらつきの範囲だと見ています。

## 9. コードの見直しで見つけた問題（2026-11-03）
