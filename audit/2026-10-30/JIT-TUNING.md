# JIT の負荷とヒープ 128 MB の調査（2026-10-31）

GC の比較（`GC-COMPARISON.md`）で、どの GC でも JIT がプロセスの CPU の 55〜60% を占めていました。
その JIT の負荷を下げられるか、またヒープを 144 MB から 128 MB に下げて問題がないかを、本番と同じ箱で調べました。

## 1. 結論

**`-XX:TieredStopAtLevel=1`（C1 だけでコンパイルする）と `-Xmx128M` の組み合わせが、高密度化にはいちばん良い結果でした。**

| 設定 | 1 台が箱から取るメモリ（anon のピーク） | 1 試合目の CPU | 慣れたあとの CPU | tick の平均 | Full GC |
|---|---|---|---|---|---|
| 今の本番（C2 あり、144 MB） | 251 MB | 0.103 コア | 0.046 コア | 0.7〜1.1 ms | 3 試合で 0 回 |
| C2 あり、128 MB | 246 MB | 0.099 コア | 0.040 コア | 0.6〜0.9 ms | 3 試合目に 1 回（104 ms、コードキャッシュが原因） |
| C2 あり、試合で学習した AOT | 229 MB | 0.081 コア | 0.040 コア | 0.7〜0.8 ms | 3 試合で 0 回 |
| C1 だけ、144 MB（2 回） | 211〜213 MB | 0.057〜0.062 コア | 0.055〜0.057 コア | 1.2 ms | 3 試合目に 1 回（76・94 ms） |
| **C1 だけ、128 MB** | **194 MB** | 0.06 コア前後 | 0.055 コア | 1.2 ms | 3 試合目に 1 回（81 ms） |

- **「JIT が 55〜60%」は、起動した直後の 1 試合目だけのことでした。**
  - 本番の SG は、試合が終わっても JVM を再起動しません（Cleanup のあと Lobby に戻る）。
  - これまでのベンチは、試合ごとに JVM を起動し直していたので、毎回 1 試合目を測っていました。
  - 1 つの JVM で 3 試合を流すと、C2 の JIT の CPU は 19.1 → 7.0 → 1.6 秒と減っていきます。
- **C1 だけにすると、メモリが 1 台あたり約 38 MB 減ります。** 2 回測って、同じ結果でした。
  - C2 のコンパイラが使う作業用のメモリ、C2 のコード、プロファイル（MethodData）がなくなるためです。
  - 128 MB と組み合わせると、今の本番より **57 MB（23%）** 減ります。
- **C1 だけにすると、起動直後の CPU が大きく下がります。**
  - 1 試合目の CPU は 40% 減ります。
  - 試合前の準備（preload）の CPU は、0.29 コアから 0.09 コアまで下がります。
- **そのかわり、慣れたあとの CPU は約 3 割増えます**（0.042 → 0.056 コア）。
  - それでも、CPU で決まる台数は、メモリで決まる台数よりずっと多いままです（4 節）。
  - tick は 0.7 ms から 1.2 ms に延びますが、持ち時間の 50 ms に比べれば、ごくわずかです。

## 2. 計測の条件

- **箱**：VPS-B（ConoHa、2 vCPU・960 MB、OpenJDK 25.0.4.1）。計測の間は sg1・sg2 を止めました。
- **jar**：このブランチの Athena（`j25-final3`）、GC は Parallel。
- **負荷**：ボット 20 体で、Lobby_Games（重いマップ）の試合を、**1 つの JVM のまま 3 試合**続けて流しました（`J25_MATCHES=3`）。
  - 段階の長さは、GC の比較と同じです（live 120 秒、deathmatch 最大 180 秒）。
- **AOT キャッシュ**：設定ごとに、本番とは別の場所に作りました。
  - 通常の設定は、本番と同じく「起動して止めるだけ」で学習しています。
  - 「試合で学習した AOT」は、学習の回（AOTMode=record）で 1 試合を流し、その記録からキャッシュを作りました。
- **測ったもの**：5 秒ごとの、スレッドごとの CPU（C1・C2 のコンパイラのスレッドと、プロセス全体）。
  - これを試合の区切り（Lobby に戻った時刻）で分け、試合ごとの JIT の CPU を出しました（`analyze_jit.py`）。

## 3. 結果

### 3.1 試合ごとの CPU と JIT（秒）

| 設定 | 起動 | 1 試合目 | 2 試合目 | 3 試合目 |
|---|---|---|---|---|
| 今の本番（C2、144 MB） | 3.8（JIT 2.2） | 33.9（JIT 19.1） | 19.0（JIT 7.0） | 10.7（JIT 1.6）※232 秒 |
| C2、128 MB | 4.7（2.5） | 33.1（19.6） | 20.1（7.3） | 13.4（2.0） |
| C2、試合で学習した AOT | 5.8（3.7） | 26.3（12.8） | 14.8（2.0） | 14.4（1.7） |
| C1、144 MB（1 回目） | 3.2（0.6） | 20.2（1.2） | 19.6（0.2） | 19.3（0.0） |
| C1、144 MB（2 回目） | 2.1（0.3） | 21.6（1.4） | 15.8（0.1） | 17.3（0.1） |
| C1、128 MB | — | 14.4（1.2）※196 秒分 | 21.5（0.3） | 19.2（0.1） |

※ 1 試合の長さは 290〜380 秒です（deathmatch が早く終わると短くなる）。比べるときは、1 秒あたりのコア数で見てください。
「C1、128 MB」の起動と 1 試合目の前半は、CPU の記録が始まるのが遅れたため欠けています。

試合前の準備（pre-game、preload を含む 30 秒）の CPU（コア）：

| 設定 | 1 試合目 | 2 試合目 | 3 試合目 |
|---|---|---|---|
| 今の本番 | **0.294** | 0.063 | 0.037 |
| C2、128 MB | 0.285 | 0.059 | 0.081 |
| C2、試合で学習した AOT | 0.264 | 0.037 | 0.056 |
| C1、144 MB（2 回） | **0.083・0.091** | 0.054・0.044 | 0.047・0.074 |
| C1、128 MB | 0.086 | 0.055 | 0.057 |

- GC の比較で「全台が同時に preload すると 0.29 コア」としていたのは、起動したばかりの 1 試合目の数字でした。2 試合目からは、C2 でも 0.04〜0.08 コアです。
- 起動したばかりのサーバーが同時に試合を始める場面は、デプロイや箱の再起動のあとに起きます。C1 だけにすると、この場面の CPU が 3 分の 1 になります。

### 3.2 メモリ

| 設定 | RSS のピーク | anon のピーク | 終了の直前の anon |
|---|---|---|---|
| 今の本番（C2、144 MB） | 334 MB | 251 MB | 234 MB |
| C2、128 MB | 330 MB | 246 MB | 224 MB |
| C2、試合で学習した AOT | 321 MB | 229 MB | 216 MB |
| C1、144 MB（2 回） | 295・293 MB | 213・211 MB | 213・211 MB |
| **C1、128 MB** | **276 MB** | **194 MB** | 193 MB |

- **1 試合だけのベンチでは、メモリを少なく見積もっていました。** 1 試合では Parallel の anon は 201 MB でしたが、3 試合続けると 251 MB まで増えます。
  - GC のあとに残るヒープが、試合ごとに約 16 MB ずつ増える（54 → 70 → 86 MB）ためです。
  - 漏れではありません。Full GC のあとは 48〜49 MB に戻ります。試合ごとに old 領域へ移ったゴミが、Full GC まで溜まっていくだけです。
- **ヒープを 128 MB にして減るのは、5〜16 MB です。** 3 試合の間では、144 MB の old 領域も使い切っていないため、差は小さく出ます。長く動かすと old 領域を使い切るので、差は約 16 MB になります。

### 3.3 ヒープ 128 MB の GC と、試合ごとに増えるヒープ

Full GC は、7 本の中で次のとおりでした（学習の回を除く）。

| 設定 | Full GC | 原因 | GC の前 → 後 |
|---|---|---|---|
| C2、144 MB | なし | | |
| C2、128 MB | 3 試合目に 1 回、104 ms | **コードキャッシュ**（CodeCache GC Threshold） | 89 → 45 MB |
| C2、試合で学習した AOT | なし | | |
| C1、144 MB（2 回） | 3 試合目に 1 回、76・94 ms | ヒープが一杯（Allocation Failure） | 120・122 → 48 MB |
| C1、128 MB | 3 試合目に 1 回、81 ms | ヒープが一杯（Allocation Failure） | 113 → 47 MB |

- C2 の 128 MB の回の Full GC は、ヒープではなく、C2 が作ったコードの量がきっかけでした。C1 だけにすると、このきっかけはなくなります。
- C1 だけの回は、ヒープが一杯になって Full GC が起きています。144 MB でも 128 MB でも、3 試合目です。
  - C1 は、C2 のようにオブジェクトの割り当てを消す最適化（エスケープ解析）をしないので、割り当てが少し多くなります（Young GC が 3 試合で 13 → 15 回）。
  - そのぶん old 領域が埋まるのが少し速く、144 MB と 128 MB の差（old 領域で約 11 MB）は、3 試合の中では効いてきませんでした。
- **つまり、C1 だけ・128 MB では、3 試合に 1 回くらい、80 ms 前後の Full GC が起きます。** 1 回の停止は 2 tick 分です。

**試合ごとにヒープが増えるのは、漏れではありません。** 試合のワールドの作り方による、世代別の GC のふつうの動きです。

1. SurvivalGames は、試合のたびにマップをテンプレートから新しいワールドとして読み込みます（`Arenas.load` → `Athena.loadTemplateWorld`）。
2. 試合の範囲のチャンク（Lobby_Games で約 1,300 個）は、`Athena.pinChunks` と `preloadChunks` で、試合が終わるまでメモリに置かれます。1 個あたり約 11 KB なので、1 試合で約 14 MB です。
3. これらは試合の間ずっと生きているので、Young GC を何回か越えたところで old 領域に移されます。
4. 試合が終わるとワールドは捨てられ（`Bukkit.unloadWorld`）、old 領域にあるこの約 14 MB がゴミになります。
5. Young GC は old 領域を片付けないので、このゴミは Full GC まで残ります。試合ごとに増える約 16 MB は、ほぼこの 1 試合分のワールドです。

Full GC のあとは、どの回も 45〜48 MB まで戻っています。捨てたワールドを SurvivalGames も Athena もつかみ続けてはいない、ということです（「Could not unload」の警告も、どの回にも出ていません）。

### 3.4 試合で学習した AOT キャッシュ### 3.4 試合で学習した AOT キャッシュ

- JDK 25 の AOT キャッシュは、学習の回のメソッドのプロファイルも保存します（JEP 515）。試合を 1 回流して学習させると、JIT は試合で使うメソッドを、プロファイルを取り直さずに最適化できます。
- その結果、1 試合目の CPU は 22% 減り（0.103 → 0.081 コア）、JIT は 19.1 秒から 12.8 秒に減りました。2 試合目も、JIT は 7.0 秒から 2.0 秒に減りました。
- ただし、学習には「本物の試合を 1 回、record モードで流して止める」という手順が要ります。今の入れ替えのスクリプトは、起動して 25 秒で止めているので、その手順を足す必要があります。
- C1 だけにする場合は、そもそも JIT がほとんど動かないので、この学習の効果はほとんどありません。

### 3.5 試合のワールドを捨てたあとに Full GC を頼む（SurvivalGames）

3.3 の対策として、SurvivalGames の Cleanup で、試合のワールドを捨てた 1 秒後に `System.gc()` を呼ぶようにしました（v1 は `feature/gc-after-match-v1`、v2 は `feature/gc-after-match-v2`）。C1 だけ・128 MB で、同じく 3 試合を流しました（`j25_308_c1128gc_LB`）。
この回だけは、本番の sg1・sg2 を止めずに流しています。GC の動きを確かめるための計測で、CPU は比べていません。

| | 対策なし（`j25_306`） | 対策あり（`j25_308`） |
|---|---|---|
| Full GC | 3 試合目の**試合中**に 1 回（81 ms） | 毎試合の**ロビー**で 1 回（68〜83 ms） |
| 試合中の Full GC | 1 回 | **0 回** |
| 試合中の、GC のあとに残るヒープ | 53 → 71 → 86 MB と増える | 60 → 46 → 45 MB で増えない |
| ロビーでの Full GC のあと | | 26〜28 MB（前の試合のワールドが片付いた量） |
| anon のピーク | 194 MB | **177 MB** |

- Full GC の停止は、誰も戦っていないロビーに移り、試合中には起きなくなりました。
- old 領域が毎試合空に近い状態から始まるので、1 台あたりのメモリのピークも 17 MB 下がりました。

## 4. 箱ごとに何台載るか（見積もりの更新）

前提は `GC-COMPARISON.md` と同じです（OS の分 350 MB、共有される jar と AOT キャッシュ 85 MB、メモリの余裕 10%、CPU は vCPU の 70% まで）。
ただし、1 台あたりのメモリは、**3 試合を続けたときの anon のピーク**で数えます。

### メモリで決まる台数

| 設定 | 2 vCPU・1 GB | 3 vCPU・2 GB | 4 vCPU・4 GB |
|---|---|---|---|
| 今の本番（C2、144 MB、251 MB） | 1 | 5 | 12 |
| C1、144 MB（212 MB） | 2 | 6 | 14 |
| **C1、128 MB（194 MB）** | **2** | **6** | **15** |

- 1 GB の箱で今 2 台が動いているのは、2 台が同時にピークになることがほぼないためです。見積もりでは 1 台分の余裕しかありません。

### CPU で決まる台数

| 設定 | 2 vCPU | 3 vCPU | 4 vCPU |
|---|---|---|---|
| C2、慣れたあと（0.042 コア） | 33 | 50 | 66 |
| C1、慣れたあと（0.056 コア） | 25 | 37 | 50 |
| C2、起動直後に全台が同時に preload（0.29 コア） | 4 | 7 | 9 |
| **C1、起動直後に全台が同時に preload（0.09 コア）** | **15** | **23** | **31** |

- 慣れたあとは、どちらでも CPU よりメモリが先に頭打ちになります。
- C2 では、デプロイのあとに全台が同時に 1 試合目を始めると、CPU が先に頭打ちになります（4 GB の箱で 9 台）。C1 だけにすると、この心配がなくなります。
- ボットの負荷での数字です。本物のプレイヤーは、ボットより CPU を使う可能性があります。

## 5. おすすめ

1. **`-XX:TieredStopAtLevel=1` と `-Xmx128M` にする。** 1 台あたりのメモリが 57 MB 減り、4 GB の箱で 3 台多く載ります。起動直後の CPU の山もなくなります。
   - 慣れたあとの CPU は約 3 割増えますが、tick は 1.2 ms で、持ち時間に十分な余裕があります。
   - 本物のプレイヤーでの CPU は、まだ測っていません。本番に入れたら、1〜2 日、sg1・sg2 の CPU と tick を見てください。
2. **Full GC を、試合の合間に起こす**（SurvivalGames の側。3.5 で入れて確かめました）。試合のワールドを捨てた直後（Cleanup の終わり）に `System.gc()` を呼べば、そのワールドの分が、誰も戦っていないときに片付きます。old 領域は毎試合、空に近い状態から始まるので、試合中の 80 ms 前後の Full GC がなくなります。いつ誰も戦っていないかを知っているのはプラグインなので、Athena ではなく SurvivalGames に入れるのが合っています。
3. **C2 のままにするなら、試合で AOT キャッシュを学習させる。** 1 試合目の CPU が 22% 減ります。入れ替えのスクリプトの手順を変える必要があります。
