# Java 25・性能の修正案：実装と計測の結果（2026-10-30）

[REPORT-JAVA25-PERF.md](REPORT-JAVA25-PERF.md) の修正案に取り組み、すべての項目で作業前と作業後を計測しました。

## 1. まとめ

### 1.1 採用したもの

| 項目 | 内容 | 作業前 → 作業後（実測） |
|---|---|---|

## 2. 作業ブランチと計測の環境

- ブランチは `perf/java25-audit-2026-10-30` です。ルート、生成した Server、生成した API の 3 つとも同じ名前で、`origin/master`（`4b1e568`）から切りました。**push はしていません。**
- 修正案ごとにブランチを分けることはしませんでした。パッチの番号（0375〜）が順番に付くので、ブランチを分けると番号がぶつかり、マージのたびに作り直しが必要になるためです。その代わり、**修正案 1 つにつき 1 コミット**にしました（§5）。
- 計測の環境は 3 つです。
  - **Mac（M1 Max、GraalVM 25）**：マイクロベンチ（毎回新しい JVM で、作業前と作業後を交互に 3 プロセスずつ）と、本物のサーバーにボット 20 体を入れた計測（`mapbench.py` と `MapProbe`）。
  - **Mac 上の Linux VM（colima、Temurin 25.0.4）**：時計を動かす計測（J01）と、起動時の計測（J02/J06/J03）。
  - **VPS の sgbench3（本番と同じ VPS-B、Temurin 25.0.4.1）**：試合全体を通した計測を 12 試合。
- テスト：Server **5,632 件**、API **992 件**、失敗 0（スキップは 1 件と 3 件。作業前は 5,630 件と 988 件）。足したテストは `AthenaEncoderFailureTest`（2 件）と `AthenaEventExecutorTest`（4 件）です。どちらも、作業前のクラスで失敗することを確かめました。
- 計測用のスクリプト、プローブ、生の結果は [java25-bench/](java25-bench/) に置きました。

## 3. 項目ごとの詳細

### J01 — tick の時刻源（server 0375）

**計測の方法**
- Linux VM のコンテナでサーバーを動かし、`date -s` で VM の時計を 2 秒戻し、そのあと 3 秒進めました。
- 計測用のプラグイン（TickProbe）が、毎 tick の開始の時刻を `nanoTime` で記録します。
- 計測中に、VM 自身の時刻の同期も時計を戻しました。そのため、1 回の計測で時計は 3〜4 回動いています。

**結果**

| | 時計の移動 | 最長の間隔 | 1 秒を超えた停止 | 停止の合計 | 連続で回った tick（10 ms 未満の間隔） |
|---|---|---|---|---|---|
| 作業前 1 | 3 回 | 2,867 ms | 2 回 | 4,826 ms | 60 |
| 作業前 2 | 4 回 | 3,047 ms | 2 回 | 4,998 ms | 100 |
| 作業後 1 | 4 回 | 61.9 ms | 0 | 0 | 0 |
| 作業後 2 | 4 回 | 59.5 ms | 0 | 0 | 0 |

時計が動かない間の tick の間隔は、作業前後とも中央値 49.9〜50.0 ms で同じでした。

**変更内容**
- `ab` と `R` を、ナノ秒の `athenaNextTick` と `athenaLastSkip` に置き換えました。
- `aL()`（ウォッチドッグ用）は、これまでどおり壁時計の値を返します。

### J04 — 書き込みに失敗したパケット（server 0376）

**計測の方法**
- プレイヤー名に null が入ったチームパケットを書き込み、続けて keep-alive を送ります。
- 送られたバイト列を、1.8 のクライアントと同じ手順で読みます。

**結果**
- 作業前：17 バイト（圧縮ありは 20 バイト）が送られ、クライアントは `Bad VarInt decoded` で読み込みに失敗します。
- 作業後：0 バイトで、keep-alive だけが届きます。ログには、捨てたパケットのクラス名が出ます。

**変更内容**
- `PacketEncoder` は、失敗したらバッファを空にします。
- `PacketPrepender` と `PacketCompressor` は、空のバッファに長さを付けずに通します。

### J02・J06 — 起動の設定（server 0377 と `deploy/start-small.sh`・`paperclip/build.gradle.kts`）

**計測の方法**：Linux コンテナで、本番と同じ 144M のヒープとフラグで起動し、各条件を 2 回ずつ測りました。

| 条件 | WARNING の行数 | スレッド数 | RSS | 起動にかかった時間 |
|---|---|---|---|---|
| 作業前（`start-small.sh` 方式） | 8 | 26〜27 | 237〜244 MB | 1.24 秒 |
| 作業前の jar に新しいフラグだけ | 0 | 27 | 245〜246 MB | 1.19〜1.29 秒 |
| 作業後 | 0 | 26 | 246〜253 MB | 1.29〜1.38 秒 |
| 作業前（`java -jar`） | 8 | 30 | 326〜335 MB | 1.25〜1.31 秒 |
| 作業後（`java -jar`） | 4 | 29 | 323〜326 MB | 1.18〜1.29 秒 |

- RSS と起動にかかった時間の差は、計測のばらつきの範囲です。
- スレッドの一覧から「Server Infinisleeper」が消えたことを確かめました。
- 新しい `start-small.sh` でも、AOT キャッシュの学習・作成・使用が通ります。キャッシュを使った起動は 0.58 秒でした。
- `java -jar` で残る 4 行は Unsafe の警告です。これは jar の manifest では止められません。
- キャッシュの掃除は、「使われてから 7 日以内のキーは残す」ようにしました。模擬した 4 台の同時起動では、作業前は起動の直前のキー A が消えていましたが、作業後は残りました。
- JDK のパスの固定は、変えていません。VPS は apt の `/usr/bin/java` を使っているので、パスを固定しても更新は止まりません。止めたい場合は、`apt-mark hold` などの運用で決めることになります。
- bStats は変えていません。外部への送信を続けるかどうかは、運用の判断だからです。

### P03 — イベントの呼び出し（api 0051）

**計測の方法**
- 4 つのプラグインが `PlayerMoveEvent` を 1 つずつ受け取る形にし、`registerEvents` と `callEvent` の実際の経路で、1 回あたりの時間を測りました。
- 「多様」の条件では、別の 16 種類のリスナーを同じ経路で動かしてから測ります。
- 毎回新しい JVM で、作業前と作業後を交互に 3 プロセスずつ、各 5 ラウンド測りました（中央値）。

**結果**：§1.1 のとおりです。

**変更内容**
- `LambdaMetafactory` を使い、リスナーのクラスと同じ nest に、ハンドラーを直接呼ぶクラスを作ります。
- static のハンドラーや、作れなかった場合は、これまでの reflection の経路を使います。

**本番への影響**：20 人で 1 秒に約 400 回の `PlayerMoveEvent` に換算すると、1 秒あたり 10 µs 程度です。tick への影響はごくわずかです。

### J03 と 0380 — Netty 4.2 とアロケータ（server 0378, 0380）

- 依存を `netty-handler`・epoll・io_uring の 4.2.19 にしました。Linux のコンテナで io_uring で起動することを確かめました。
- `netty-all` を 4.2 にすると、QUIC のネイティブライブラリなどで jar が 12 MB 増えます。そのため、必要なモジュールだけを指定しました。本番の 2 つのプラグイン（SurvivalGames とハブの Athena.jar）は、手元のビルドで確認したところ Netty を参照していません。
- VPS で比べたところ、Netty 4.2 の既定の adaptive アロケータでは、RSS のピークが 308〜316 MB（4 試合）でした。Netty 4.1 の版は 294〜302 MB です。
- アロケータを pooled にすると 300〜302 MB（2 試合）に戻ったので、`Main` で pooled を既定にしました（0380）。本番のフラグ `maxOrder=7` も、pooled にしか効きません。

### J05 — 依存ライブラリ（api 0052, server 0379）

| ライブラリ | 作業前 → 作業後 | 既知の脆弱性（OSV） |
|---|---|---|
| Log4j | 2.25.3 → 2.25.5 | 4 → 0 |
| Gson（実際に入っていた版） | 2.8.0 → 2.10.1 | 1 → 0 |
| SnakeYAML | 1.15 → 1.33 | 8 → 1（※） |
| commons-io | 2.4 → 2.20.0 | 2 → 0 |
| commons-lang3 | 3.3.2 → 3.19.0 | 1 → 0 |
| Guava | 宣言を 17 → 18.0（実際に入っていた版） | 4 のまま（21 以降では古いプラグインが壊れる） |

※ 残る 1 件は Constructor の問題（CVE-2022-1471）で、Bukkit が使う SafeConstructor の経路では起きません。

- 速度（作業前後を交互に 3 プロセスずつ）：
  - チャットの JSON の変換（往復）：3,915 → 3,263 ns（−17%）
  - `spigot.yml` の YAML の読み込みと書き出し：361 → 350 µs
- commons-io 2.20 では `IOUtils.readLines` が `IOException` を投げなくなったので、`LocaleLanguage` を直しました。バイナリの互換は保たれます。ソースから再コンパイルするプラグインだけが影響を受けます。

### P04 — Netty のスレッド数（server 0381）

  - tick の平均：2.88・3.28 ms と、2.63・3.07 ms。
- 既定値を 1 にしました。`spigot.yml` に値が書いてあるサーバーは、その値のままです。

### Mac での試合全体の比較（参考）

- Moonbase_9 にボット 20 体を入れ、ウォームアップ 90 秒・計測 150 秒で、作業前と作業後を交互に 2 回ずつ測りました。

## 4. VPS での計測の手順と後片付け

- 本番の sg1/sg2 は `/opt/mc/shared-cache` のキーで AOT キャッシュを共有しています。今の `start-small.sh` は、新しい順に 3 つより古いキーを消します。そのため、ベンチで新しい jar を 3 種類以上起動すると、**本番のキーが消えて、次の再起動で学習の起動（RSS の山）が起きる**ところでした。
- そこで、sgbench3 の `start-bench.sh` を一時的に差し替え、`ATHENA_CACHE_ROOT=/opt/mc/sgbench3/aot-cache` で動かしました。
- sgbench3 の `athena.yml` は、本番と同じ io_uring オン・圧縮レベル 1 にして測りました。
- 計測のあと、次のことを済ませました。
  - `start-bench.sh`・`paperclip.jar`・`athena.yml` を元に戻した。
  - ベンチ用のスクリプトと aot-cache を消した。
  - sgbench3 が停止していることを確かめた（空きメモリ 591 MB）。
  - 本番のキー `9a1e060c…` が残り、sg1/sg2 がそのキーで動いていることを確かめた。
- 退避したファイルは、VPS の `/root/sgbench3-*.before-j25.*` に残しています。

## 6. 本番に入れるときの注意

- `start-small.sh` のフラグが変わるので、AOT キャッシュのキーが変わります。入れ替えたあと最初の起動は、学習の起動になります（V01 で記録した、メモリが一時的に増える件）。
- J03 と J05 は、バイナリの互換を保つ範囲の更新です。ただし、Netty の内部や commons-io を直接使う他人のプラグインを入れる場合は、事前に起動を確かめてください。今の本番のプラグインは影響を受けません。
- P03 は、イベントの呼び出し方を変えます。SurvivalGames を含む VPS の 12 試合では問題は出ませんでしたが、イベントの受け取りを個別に確かめたわけではありません。
