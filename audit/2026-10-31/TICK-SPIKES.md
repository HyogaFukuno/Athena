# 50 ms を超える tick の原因と対策（2026-10-31）

Sol の再調査（`GC-RECHECK.md`）と私の計測（`audit/2026-10-30/JIT-TUNING.md`）の両方で、どの GC でも、試合全体の最大の tick が 80〜140 ms になっていました。その原因を、本番と同じ VPS-B（2 vCPU・960 MB）で調べて直しました。

## 1. 結論

50 ms を超える tick は 3 種類だけで、どれも試合中（pregame の後半・live・deathmatch）ではなく、起動直後かロビーで起きていました。

| 遅い tick | 原因 | 対策 | 前 → 後 |
|---|---|---|---|
| 起動後、最初のプレイヤーたちが入るとき | AOT キャッシュにないクラス約 820 個を、jar から読み込んで検証していた | AOT キャッシュの学習の回で、1 試合を流す | 115〜219 ms → **41 ms** |
| 最初の試合のマップの読み込み | 同じく、クラス約 150 個の読み込みと C1 のコンパイル | 同上 | 73〜95 ms（50 ms 超が 2〜3 tick）→ 70 ms（1 tick） |
| ロビーの Full GC（`System.gc()`） | ヒープ全体の詰め直し（44 ms）とクラスのアンロード（17〜21 ms） | `-XX:-UseMaximumCompactionOnSystemGC` | 85〜101 ms → 57〜81 ms |

- 試合中に 50 ms を超えた tick は、JFR を付けずに流した 5 本（13 試合、ロビーで GC する版）で 0 回でした。
- live 中に 1 回だけ出た 79 ms は、JFR を付けた回でしか起きていません。そのときサーバースレッドは Java のコードを動かしておらず、クラスの読み込みも GC もなく、CPU もほぼ空いていました。JFR そのものか、VPS の CPU を一瞬取られた（steal）ことによる外れ値と見ています。

## 2. 調べ方

- VPS-B の sgbench3 で、本番と同じ設定（Parallel・C1 だけ・128 MB・ロビーで GC する SurvivalGames v1）にし、Lobby_Games・ボット 20 体で、1 つの JVM のまま 2 試合を流しました。計測の間は、本番の sg1・sg2 を止めました。
- tick の時間は、Athena の athena-diag（100 tick ごとの最大と、50 ms を超えた数）で取りました。それを試合の場面（ボットが記録したチャット）と突き合わせました。
- 遅い tick の中身は、次の 2 つで調べました。
  - **JFR**：1 ms ごとのサンプリング（`jdk.ExecutionSample`）、クラスの読み込みの数（`jdk.ClassLoadingStatistics`）、ファイルの読み込み、ロック、スレッドの待ち。
  - **GC と safepoint のログ**：`-Xlog:gc+phases=debug,safepoint`。
- サーバースレッドが続けて 30 ms 以上 Java のコードを動かしていた区間は、`tick-spikes/jfr_bursts.py` で切り出しました。
- Mac の Linux VM（CPU 2 個に制限）でも同じ試合を流しましたが、VPS より約 2 倍速く、起動後に 50 ms を超えた tick は出ませんでした。そのため、原因の確定と対策の確認は、すべて VPS で行いました。

## 3. 原因

### 3.1 最初のプレイヤーの参加と、最初のマップの読み込み：クラスの読み込み

最初のプレイヤーたちが入った 5 秒の間に、読み込み済みのクラスは 7,280 個から 8,104 個に増えました。JFR には、patched jar と SurvivalGames.jar からのファイルの読み込みが並んでいました。

- AOT キャッシュに入っているクラスは、読み込み・リンク済みの状態で、ファイルから写されるだけです。入っていないクラスは、jar から読んで、解析し、検証してから使われます。
- これまでの学習の回は「起動して、すぐ止める」だけでした。プレイヤーの参加（ログイン、パケット、インベントリ、チャットなど）や、試合（マップの読み込み、試合の終わり）で初めて使うクラスは、キャッシュに入っていませんでした。
  - 最初のマップの読み込みでは約 150 個、最初の試合の終わりでは約 1,000 個を読み込んでいます。
- クラスを読み込んで検証している間、サーバースレッドは JVM の中にいるので、JFR の実行サンプルには映りません。そのため、遅い tick に Java のメソッドが何も映っていませんでした。
- 2 試合目からは、クラスがもう読み込まれているので、起きません。本番では、デプロイやサーバーの再起動のあとの 1 試合目に起きていました。

### 3.2 ロビーの Full GC：詰め直しとクラスのアンロード

VPS での `System.gc()` の内訳（85 ms の回）は、次のとおりでした。

| 段階 | 時間 |
|---|---|
| 生きているオブジェクトの印付け | 21 ms |
| クラスのアンロード（C1 のコードの後始末を含む） | 17 ms |
| 移動先の計算（Forward） | 12 ms |
| 参照の書き換え（Adjust Pointers） | 19 ms |
| 移動（Compaction） | 13 ms |

- Parallel GC は、`System.gc()` のときだけ、old 領域の先頭の「ほとんど生きている部分」も含めて、ヒープ全体を詰め直します（`UseMaximumCompactionOnSystemGC`、既定でオン）。
- クラスのアンロードは、1 回の Full GC で 59 個です。`-XX:-ClassUnloading` で外せば 17〜21 ms 縮みますが、試合ごとに作られるクラスが溜まり続けるおそれがあるので、使いませんでした。

## 4. 対策と結果

### 4.1 計測の結果（Lobby_Games、1 つの JVM で 2 試合、VPS-B）

| 設定 | 最初の参加 | 最初のマップの読み込み | ロビーの Full GC | 50 ms を超えた tick（起動 / 1 試合目 / 2 試合目） |
|---|---|---|---|---|
| 今の本番と同じ（JFR あり、`j25_311`） | 219 ms | 95 ms | 85・101 ms | 0 / 4 / 2 |
| 詰め直しを軽く（`j25_312`） | 115 ms | 73 ms（3 tick） | 73・81 ms | 0 / 4 / 1 |
| ＋ 試合で学習した AOT（`j25_314`） | **41 ms** | 70 ms（1 tick） | **57・74 ms** | 0 / **1** / 1 |

- 試合で学習した AOT キャッシュでは、2 試合を通して 50 ms を超えた tick が、最初のマップの読み込みとロビーの Full GC の 1 回ずつだけになりました。
- 詰め直しを軽くする設定で、Full GC の詰め直しの部分は 44 ms から 27〜38 ms に減りました（移動先の計算 12 → 3〜5 ms、移動 13 → 8〜11 ms）。
- 学習したキャッシュはクラスが多いぶん大きくなりますが、ファイルとして共有されるので、1 台あたりの anon は変わりません（170 MB と 174 MB）。

### 4.2 本番への入れ方

1. `deploy/start-small.sh`（ArcanaServers の `common/start-small.sh`）に、`-XX:-UseMaximumCompactionOnSystemGC` を足しました。
   - 設定が変わるので、AOT キャッシュのキーも新しくなり、次の起動が学習の回（record）になります。
2. 学習の回では、ボットで 1 試合を流します。
   - sgbench3 を、本番と同じ jar・同じ設定・本番のキャッシュの置き場所（`/opt/mc/shared-cache`）で起動し、ボット 20 体で 1 試合を流して止めます。
   - 次に起動した sg1 が、その記録から本番のキャッシュを作ります。
   - キャッシュは、jar・JDK・起動の設定ごとに作り直しになります。Athena の jar や JDK、起動の設定を変えたときは、同じ手順で学習させ直します。プラグインの入れ替えだけなら要りません。

## 5. 残っていること

- **最初の試合のマップの読み込み（70 ms、1 tick）**：学習したキャッシュでも残りました。テンプレートのワールドを開く処理（`AthenaSectionStore` の読み込みなど）と、まだ C1 でコンパイルされていないコードが重なっています。起動後の 1 試合目にだけ起きます。
- **ロビーの Full GC（57〜81 ms）**：誰も戦っていないロビーで、試合ごとに 1 回起きます。さらに縮めるには、次のような方法があります。
  - 試合のワールドのチャンクのメモリ（ブロックや明るさの配列）を、次の試合のワールドで使い回す（Athena）。old 領域にゴミが溜まらなくなり、Full GC そのものが要らなくなります。変更は大きくなります。
  - old 領域が埋まってきた試合でだけ `System.gc()` を呼ぶ（SurvivalGames）。最大の長さは変わりませんが、回数は 3 分の 1 くらいになります。

## 6. ロビーの Full GC の回数を減らす（続き）

### 6.1 試合ごとのゴミの中身

Mac の Linux VM で 1 試合を流し、試合中とワールドを捨てた直後のヒープのクラス別の量（`GC.class_histogram`）を比べました（`match-garbage/histo-*.txt`）。1 試合で約 30 MB がゴミになっていて、ブロックと明るさの配列はヒープの外（テンプレートのファイルを mmap した領域）にあるので、含まれていません。

| 中身 | 量 |
|---|---|
| チャンクのパケットのキャッシュ（`byte[]`、圧縮済み） | 約 8〜11 MB |
| `int[]`（高さのマップなど） | 4 MB |
| GC の詰め物（`FillerElement`、実際のゴミではない） | 4 MB |
| セクションと明るさの配列のオブジェクト（1 チャンクに 16 個） | 3.3 MB |
| エンティティのリストと、その反復子（1 チャンクに 16 本） | 2 MB |

チャンクごとの小さなオブジェクトが何万個も集まったもので、ワールドをまたいで使い回すのは危ういので、作らないようにする方向で減らしました。

### 6.2 対策

1. **Athena（server 0383）**：
   - エンティティのリスト：最初のエンティティが入るまで、1 つの共有の空リストを指します。空のリストを反復しても、反復子を作りません。
   - セクション：空気だけで、明るさも初期のままで、どの列の高さより上にあるものは、チャンクに持ちません。読み出しの結果は変わりません。
2. **SurvivalGames（`LobbyGc`）**：ロビーでの `System.gc()` を、「前の試合と同じだけ増えると（1.5 倍で見積もり）、次の試合の間に old 領域の 9 割を超えそう」なときだけにします。判断は毎試合ログに 1 行出します。

### 6.3 結果（VPS-B、本番と同じ設定、Lobby_Games で 3 試合）

| | 今の本番（master ＋ 毎試合 GC） | 新しい版（master ＋ 0383 ＋ `LobbyGc`） |
|---|---|---|
| ロビーの Full GC | 3 回（56〜86 ms） | **1 回（53 ms）** |
| 50 ms を超えた tick（1・2・3 試合目） | 2・1・1 | 2・1・**0** |
| 試合ごとの old 領域の増え方 | 約 16 MB | 12〜14 MB |
| anon のピーク | 168 MB | 168 MB |

- 新しい版は、1 試合目のあとに 1 回片付けたあと、2 試合目（43 MB）と 3 試合目（56 MB）は「次の試合でも収まる」と判断して見送りました。次は 4 試合目のあとに片付ける見込みで、ロビーの Full GC は 3 試合に 1 回くらいになります。
- 1 試合目の 2 回は、起動直後のクラスの読み込みです（sgbench3 の AOT キャッシュは起動して止めるだけで学習させたもの）。
- anon のピークが変わらないのは、3 試合の間に old 領域が同じくらいまで埋まるためです。

## 7. 資料

- 生の結果は `tick-spikes/` と `match-garbage/` にあります（試合ごとの JSON・athena-diag.csv・gc.log・GC の段階別ログ・スレッドの CPU）。JFR の記録（`tick.jfr`、4.7 MB）は、`bench/results/vps-tick/` に置いたままにしています。
- 遅い区間の切り出しは `tick-spikes/jfr_bursts.py` です。
