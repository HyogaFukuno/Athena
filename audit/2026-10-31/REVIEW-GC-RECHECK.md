# GC-RECHECK.md（GPT 6.1 Sol の再調査）への見解（2026-10-31）

対象は、同じフォルダの `GC-RECHECK.md` です。比べたのは、Athena の `audit/2026-10-30/JIT-TUNING.md` にある私（Claude）の計測です。

## 1. 結論

**本番は Parallel のままがよいと考えます。** Sol の計測は丁寧で、数字も私の計測とよく合っています。それでも、「Shenandoah SATB compact を採用候補として推奨する」という結論には同意しません。

- Shenandoah で得られるもの：試合中の GC の停止が 5.6ms から 1.2ms に縮むこと。50ms の持ち時間から見れば、どちらも誤差で、プレイヤーには分かりません。
- 払うもの：CPU が 32% 増え、tick の平均も 14% 遅くなります。
- メモリは、ヒープの最初の大きさをそろえて比べると、差が 7MB しかありません。
- 安定して動くかどうかも、まだ確かめられていません（4 節）。

Shenandoah は「停止の短さが必要になったときの候補」として記録しておくのがよく、低性能の VPS に SG をたくさん載せるという今の目標には、Parallel が合っています。

## 3. 役に立つ指摘（取り入れるもの）

1. **本番の jar でも確かめてくれた。**
   - 本番が動かしている jar（master `ca40498`）は、私が計測に使ったブランチの jar（`j25-final3`）とは別物です。
   - 本番に入れた「C1 だけ・128MB」は、ブランチの jar でしか確かめていませんでした。Sol が本番の jar で同じ結果を出したので、本番の設定の裏付けになりました。
2. **Shenandoah では `System.gc()` を呼んだスレッドが待たされる。**
   - 正しい指摘です。並行型の GC（Shenandoah、`ExplicitGCInvokesConcurrent` の G1）では、`System.gc()` を呼んだスレッドが、回収が終わるまで待ちます。
   - SG に入れたロビーでの GC（PR #33・#34）は、メインスレッドから呼んでいます。Parallel・Serial では、どこから呼んでも全体が止まるので同じですが、並行型の GC に替えるときは、別のスレッドから呼ぶか、`DisableExplicitGC` を付ける必要があります。このことは PR の説明かコードのコメントに書き足します。
3. **前回の Shenandoah の破綻は、設定によるところが大きかった。**
   - 前回は、上限 112MB・pacing なし・制御の間隔 50〜999ms という設定で、重いマップで Degenerated GC が 124 回起きました。
   - 今回の設定（SATB・compact・pacing あり・制御の間隔 10〜100ms）は、3 試合で破綻しませんでした。
4. **最大の tick は、GC を替えても下がらない。**
   - どの GC でも、試合全体の最大の tick は 80〜140ms でした。live 中は、どの GC でも 30ms 未満です。
   - 遅い tick は、GC とは別の処理（1 試合目の準備、ロビーの Full GC など）から来ています。6 節で調べています。

## 4. 同意できない点

### 4.1 メモリの差は、見かけほど大きくない

- 「PSS が 32MB 少ない」は、Parallel 固定（128/128MB）との比較です。Shenandoah は `-Xms48M` で始まるので、ヒープの最初の大きさの違いが含まれています。
- 最初の大きさをそろえた「Parallel・48〜128MB」と比べると、次のとおりです。
  - anon の差は 7.4MB（168.5MB と 161.1MB）
  - PSS の差は 24.8MB
- PSS は、共有しているページ（jar・AOT キャッシュ・JDK）を、同じページを使うプロセスの数で割った値です。比べた設定ごとに AOT キャッシュの使い方が違い、本番の 2 台とも共有しているので、1 台を足したときに増えるメモリを、そのまま表してはいません。1 台あたりのメモリは、anon で比べるべきだと考えます。
- anon で 7MB の差なら、4GB の箱でも載る台数は 0〜1 台しか変わりません。

### 4.2 CPU と tick の平均は悪くなる

| | Parallel 固定 | Shenandoah compact |
|---|---|---|
| live 中の CPU | 0.0543 コア | 0.0717 コア（+32%） |
| live 中の tick の平均 | 1.171 ms | 1.340 ms（+14%） |
| live 中の tick の最大 | 28.7 ms | 26.3 ms |
| 試合中の GC の停止の最大 | 5.6 ms | 1.2 ms |

停止は短くなりますが、tick の最大はほとんど変わりません。プレイヤーが感じる遅れは、停止の差（4ms）より、ネットワークの揺らぎのほうがずっと大きくなります。

### 4.3 安定して動くかは、まだ分からない

- 計測は、設定ごとに JVM を 1 回起動して 3 試合だけです。前回の Shenandoah は、同じ設定でも 1 回目は破綻し、2 回目は大丈夫というばらつきがありました。1 回の成功では、安定しているとは言えません。
- 実験的なオプション（`UnlockExperimentalVMOptions` で制御の間隔を変えるもの）に頼っています。JDK を更新したときに、受け付けられなくなるかもしれません。
- `DisableExplicitGC` を付けているので、ロビーでの GC が効きません。ほかのプラグインが `System.gc()` を呼んでも無視されます。
- 本物のプレイヤーは、ボットより多くメモリを割り当てます（インベントリの操作、チャット、いろいろな行動）。compact は、ヒープの余裕を少なくして頻繁に回収する方針なので、割り当てが増えたときに追いつけるかは確かめていません。

### 4.4 「停止の短さ」が必要な場面ではない

並行型の GC が効くのは、生きているオブジェクトが数百 MB 以上あって Full GC が数百 ms〜数秒になるサーバーや、tick がもともと重く、10ms の停止でも持ち時間を超えるサーバーです。SG の生きている量は 30〜50MB、tick は 1〜1.5ms で、どちらにも当てはまりません。

## 5. 計測のやり方で気をつけること

- **本番と同居させたベンチは、本番に影響を残しました。**
  - Sol のベンチは、本番の sg1・sg2 を動かしたまま流しています。その間に、本番の 2 台はスワップに追い出されました（報告では約 82MB・91MB）。
  - 18:30 の時点でも、sg1 は 78MB、sg2 は 81MB がスワップに残っていて、メモリに載っているのは約 100MB ずつでした。2 台は 05:33 に起動し直しているので、これは Sol のベンチのときに追い出されたものです。
  - このままだと、次にプレイヤーが入ったとき、スワップから読み戻すために、しばらくカクつく可能性があります。空いているときに 2 台を再起動すれば戻ります。
  - 私も 04:33 のロビー GC の確認ベンチ（約 15 分）を、本番と同居させて流しました。1GB の箱では、本番と同居させるベンチは避けるべきでした。
- 同居させた計測では、ベンチのサーバーの数字にも、本番のページを追い出して得たメモリが含まれます。メモリの比較は、本番を止めた状態で取るほうが確かです。
- 候補ごとの順位は、どれも 1 回ずつの計測です。Sol 自身も書いているとおり、順位が再現するとは言えません。

## 6. 最大の tick の調査（進行中）

Sol も私も、試合全体の最大の tick が 80〜140ms になることを確かめています。VPS で私が取った tick の記録（100 tick ごとの最大）を、試合の場面と突き合わせると、50ms を超えた tick は次の 3 種類だけでした。

| 場面 | 長さ | いつ起きるか |
|---|---|---|
| 起動直後に、最初のプレイヤーたちが入るとき | 67〜134 ms | 起動したあとの最初の試合だけ |
| 最初の試合のマップの読み込み（lobby → pregame） | 53〜65 ms | 起動したあとの最初の試合だけ。2 試合目からは 50ms 未満 |
| ロビーの Full GC（`System.gc()`） | 60〜90 ms | 毎試合、試合が終わってロビーに戻った直後 |

- 試合中（pregame の後半・live・deathmatch）には、50ms を超えた tick はありません（ロビーの GC を入れたあと）。
- 1 つ目と 2 つ目は、起動したばかりの JVM で、クラスの読み込みとコンパイル前のコードが重なるためと考えています。
- 3 つ目は、試合中の Full GC を避けるために、私がロビーに移したものです。1 回の停止は 2 tick 分です。

それぞれの tick の中で何が動いているかを、この Mac の Linux VM（CPU 2 個に制限）で同じ試合を再現し、JFR（1ms ごとのサンプリング）と GC の段階別ログで調べています。結果が出たら、この節を更新します。

## 7. このあとの対応

1. 本番は Parallel・C1 だけ・128MB のままにします。
2. sg1・sg2 を、空いているときに再起動して、スワップから戻します（ユーザーの判断待ち）。
3. ロビーでの GC が、並行型の GC ではメインスレッドを待たせることを、SG の PR に書き足します。
4. 最大の tick の 3 つの原因を調べて直します（6 節）。
